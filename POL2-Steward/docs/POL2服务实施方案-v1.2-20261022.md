# POL2 服务实施方案

版本：v1.2（Agent 中立与任务级治理）  
日期：2026-10-22  
依据：[POL2 服务流程正式设计 v1.1](./POL2服务流程正式设计-v1.1-20261022.md)  
状态：实施中。已具备任务级数据模型、任务 API、步骤审计、许可消费、通用执行 Hook 和基础适配契约；已完成一次外部 PostgreSQL 与一个真实宿主的工程验收。尚未完成生产级风险分类、全适配器闭环和生产部署验收。核心服务不得依赖任何特定 Agent、客户端或运行环境；参考适配器只用于验证通用契约。

## 1. 第一阶段：整理 POL2，形成可验证的知识资产

这一阶段在我们的发布端完成。先用可版本管理的文件整理，暂不要求安装 PostgreSQL 或接入现有 Agent。未来数据库从这些文件导入，用户安装服务时直接加载发布好的知识包。

理论来源：[NaturalDAO / PoL](https://github.com/naturaldao/NaturalDAO/tree/main/PoL)。服务统一使用 POL2 名称，保留来源目录及原文原样。

### P0：冻结原文基线

工作：

1. 实施时读取最新目录，固定实际仓库提交编号；不直接把持续变化的 `main` 当成版本。
2. 保存全部正文、工程策略、目录说明及理解正文必需的附属文件，记录文件路径、字节数和 SHA-256 指纹。
3. 原始副本不改字；另建供检索使用的标准化文本，记录转换方式和对应关系。
4. 清点章节、协议、脚注、链接与图表，识别重复目录和缺失引用。外部文献列为参考来源，不能自动升级为 POL2 规则。

产物：`source-manifest.json`、`sources/`、`normalized/`、`source-inventory.md`。

验收：目录清单完整；源文件与固定提交逐一对应；指纹可重新计算；每份标准化文本能回到原始文件。冻结失败则不开始正式解释整理。

### P1：建立全文理解和概念地图

工作：完整阅读所有正文，先形成全局理解，再整理局部条款。至少覆盖基础定义、爱语、冥想智慧公理、伦理对齐协议、公共治理策略、生产公共化及公共福利协议。

每个概念记录定义、别名、来源、相关概念及易混淆之处。每项关系记录原文依据，区分原文明示与整理者推导。梳理公理、核心协议和子协议的关系，但不凭章节先后或字面强弱自行发明冲突优先级。

产物：`theory-overview.md`、`concepts.jsonl`、`relations.jsonl`、`chapter-coverage.csv`。

验收：所有章节均有阅读与覆盖记录；关键概念有原文依据；原文、解释、推导可区分；不存在把情绪词直接等同于行为结论的简化。

### P2：整理原文到治理规则的映射

把理论转成“判断时应检查什么”，不先编成敏感词黑名单或单一分数。

每条映射至少包含：

| 字段 | 内容 |
| --- | --- |
| `rule_id` | 稳定标识，与版本分开 |
| `source_refs` | 固定提交下的文件、章节、段落定位、原文片段指纹 |
| `kind` | 原文直接要求／解释／工程建议 |
| `scope` | 适用主体、场景和环节：需求、方案、操作或结果 |
| `check_questions` | 判断需要回答的问题 |
| `required_context` | 必须知道的事实或背景 |
| `conditions_and_exceptions` | 适用条件、限制和例外 |
| `related_rules` | 必须一起读取的定义、原则和相关协议 |
| `decision_guidance` | 可能的判断方向与理由要求，不把所有场景预先硬编码 |
| `status` | 候选／已验证／待澄清／失效 |

先整理以下边界：

- 判断行为与给个人贴标签；
- 实际执行与研究、引用、虚构创作、防护警示；
- 诚实表达、事实不确定性和虚假能力或亲密关系声明；
- 公共化要求：对外请求、NaturalDAO 内部生产及公共资源调用的适用差异；
- 情境理解与对个体情感、人格的推断边界；
- 公开透明与个人资料、第三方信息、凭证的披露边界；
- 公共福利权利与具体资源使用限制之间的关系；
- 公理、核心协议和子协议发生解释张力时如何处理。

产物：`rule-mapping.jsonl`、可阅读的 `rule-mapping.md`、`open-questions.md`。

验收：正式规则的来源定位和关联均有效；未明确的边界进入问题表。受未决项影响的场景标记澄清或待复核，不能以默认放行或默认拒绝掩盖缺口；不相关的整理可以继续。

### P3：建立测试集，再验证解释

每项关键原则至少设计正例、反例、边界例；适用时加入“只改一个关键条件，结论应改变”的成对测试。预期结果来自原文映射及独立核对，不能让被测模型自己出题、自己确定答案、自己宣布通过。

首批至少覆盖：

| 类别 | 测什么 |
| --- | --- |
| 理论问答 | 核心概念、协议关系、引用准确性 |
| 情境区分 | 同一表述用于研究、虚构、防护与实际执行时的区别 |
| 请求治理 | 合理需求、偏离需求、可调整手段、背景不足 |
| 结果治理 | 请求合理但输出编造、遗漏、操控或采用有问题的手段 |
| 多轮项目 | 需求变更、上下文缺失、附带问答、不同项目不可混记 |
| 资料来源 | 文件中夹带“绕过规则”等指令，不改变治理规则 |
| 缓存边界 | 相似措辞但操作对象、版本或项目背景不同 |
| 质询纠错 | 补充证据后应修正结论，或说明维持依据 |

测试记录保存问题、背景、适用条款、预期结果或允许范围、核对依据及状态。不足以确定答案的测试标为未决，不计入“已验证正确”。开发样例和保留测试分开，避免只围绕已见题目优化。

用隔离调用进行复核并保留分歧；必要时向理论维护方提出具体问题。此处是工作分步，不建立固定四角色团队，也不以多模型一致代替依据。

产物：`evaluation/dev.jsonl`、`evaluation/holdout.jsonl`、`evaluation/report.md`、`review-records.jsonl`。

验收：关键边界都有测试；预期依据可追踪；未决与失败不被隐藏。理论覆盖、引用准确、误拒和漏放分别报告；量化上线门槛在本阶段根据测试集明确写入报告，不在未测前宣称达标。

### P4：形成解释库和可靠回答种子

将通过 P3 验证的理解整理成可检索条目，保留适用范围、限制、来源和关联。准备核心理论、概念区分、协议关系等可靠回答。

每份回答保存 `answer_id`、适用问题范围、完整答案、来源、规则版本、核验记录、可见范围和失效条件。不能把“过去放行的请求”当成无条件通用答案；公共回答不夹带项目数据。

产物：`interpretations.jsonl`、`examples.jsonl`、`answers.jsonl`。

验收：正式条目均有验证记录；候选和未决内容不进入正式解释区；回答可回到对应原文，并通过释义及范围变化测试。

### 第一阶段完成标准

P0—P4 完成后，得到可阅读、可导入、可验证的 POL2 知识资产。此时可以审阅理论整理质量，但尚不能宣称服务已经能治理 Agent。

第一份交付优先给出：原文基线清单、理论概览、概念地图、规则映射和待解决问题；随后提交测试结果与可靠回答。每步记录完成情况、发现和下一步，不重复全量阅读已验证且未改动的内容。

## 2. 第二阶段：构建可安装知识包

### P5：检索、兼容性与打包

1. 根据章节、定义、完整条款和例外切分文本，保留上下文；核心原则固定加载。
2. 建立关键词与向量两路检索，补齐关联条款；以证据完整性验证，不能只测语义相似度。
3. 对比检索结果与完整相关章节，记录漏召回的定义和例外，调整分段与关联。
4. 固定向量模型、修订版本、维度、文本处理方式、检索配置和模型文件获取方式。
5. 打包原文、正式解释、可靠回答、预计算向量、关系、测试及兼容清单。数据库原生索引按后端提供兼容构件或从预计算向量本地建索引，不要求用户重新调用模型理解理论或生成全部向量。
6. 从空环境加载并执行自检，再生成发布清单和指纹。

产物：`retrieval-config.json`、`embeddings/`、`package-manifest.json`、版本化知识包和 `package-validation.md`。

验收：离线或明确依赖条件下可重复加载；指纹、来源、引用和兼容性有效；所有正式条目可检索；关键测试的必要证据可找齐。安装端是否需要下载检索模型必须明确，不能隐藏成首次启动的无期限等待。

## 3. 第三阶段：开发统一治理服务

### P6：数据库、接口和任务恢复

采用 PostgreSQL＋pgvector 作为第一版实现基线，服务接口建议 FastAPI；锁定具体版本前核实兼容性。

分别建立理论解释、项目记忆、缓存、治理记录、任务状态的数据结构与迁移。提供以下职责接口，路径在开发时固定：

- 知识包加载、自检、就绪状态和版本查询；
- 项目、任务、运行和步骤的创建、绑定、状态恢复与取消；
- 平台访问控制和数据隔离（如部署需要，必须与 POL2 判断分离）；
- 需求和方案评估、关键操作评估、产物评估；
- 质询、复核、任务取消、状态查询和恢复。

每次调用具有请求标识、来源客户端、项目和任务标识；普通问答不强制建项目。身份、账号和平台访问控制可以用于数据隔离，但不得进入 POL2 判断，也不得加分或减分。

把任务归属落实成可测试规则：明确项目绑定 → 会话已有绑定 → 新会话的明确工作区绑定；用户明确新建或切换时更新绑定。无绑定的单次问答使用独立任务；持续目标明确时自动建项目。目录只作线索，模型不能自行合并项目或迁移记忆。每种情况都测试项目、任务和状态恢复；附带问答不得改写项目目标。

新增 Task / Run / Step / Operation / Permit / AuditEvent 数据模型。Project 表示长期目标，Task 表示用户任务，Run 表示一次执行，Step 表示一次模型或规划步骤，Operation 表示有副作用的工具调用。所有步骤都写审计事件，但只有任务卡、风险门禁卡和交付卡等里程碑生成用户可见卡片。

明确接口数据契约：背景包含目标、用途、受影响对象、范围、约束、当前阶段、重要决定及未关闭问题；决定保存原始请求、证据引用、简明理由、不确定性、适用条件、规则版本、项目状态版本、产物版本及实际模型标识。模型输出不强求公开内部隐含推理；不以单一分数或自报信心代替判断。

产物：接口与数据结构说明、数据库迁移、项目路由规则、状态迁移表及自动化检查记录。表中列明每次迁移的触发事件、前置条件、失败出口与恢复位置，避免只列状态名称而没有推进机制。

状态至少区分：接收、等待澄清、待检查、允许执行、执行中、待结果检查、修订中、已交付、拒绝、阻塞、取消。持久化后再推进依赖步骤；设置超时、重试和修订预算。工具副作用不通过盲目重试恢复。

验收：重复请求不重复执行；服务中断能恢复；不同项目、任务和运行不会串用记忆；旧任务许可不能错误放行新操作；身份变化不改变同一内容和同一版本下的 POL2 结论。

任务级接口至少包括：创建任务、激活条件、提交步骤、提交最终交付、查询任务时间线和消费一次性许可。提交步骤时记录任务、运行、步骤、输入哈希和决定；普通低风险步骤返回任务范围允许，风险步骤升级完整判断。

### P7：治理判断、缓存与交付控制

接入可配置的治理模型，支持与 Agent 共用模型服务但隔离上下文；凭证单独管理。实现六种判断：理论回答、放行、附条件放行、澄清、修订、拒绝。

提供共用模型服务与单独指定治理模型两种配置，明确地址、模型名、经授权的凭证、超时和调用上下文；不自动读取或转交 Agent 凭证。形成版本化治理提示和结构化决定模板。分别验证两种配置能完成同一流程；原始资料中的指令不能覆盖治理提示。

执行流程：恢复任务背景 → 固定原则与证据检索 → 模型判断 → 引用、格式和版本校验 → 必要复核 → 保存决定。不得把程序格式检查当成语义正确性。

任务入口做完整判断并形成 Task Permit；普通低风险步骤只检查任务许可、范围、模型白名单、预算和风险触发器，不重复调用完整治理模型；目标、对象、用途、数据、工具、范围或版本变化时升级判断。

输入、方案、操作、结果分别检查；许可绑定当前任务、运行、条件和具体内容。结果同时收集事实技术证据；未经检查的草稿先缓冲。可靠回答允许轻量复用，历史判定只有关键条件一致才能复用。实现版本变更、撤销和纠错导致的缓存失效。

具体实现四项机制：

1. **检查深度选择**：理论问答和低风险步骤走轻量路径；任务入口、最终交付、实际影响较大、原则冲突、不确定判断和重要拒绝增加完整判断或隔离复核。记录选择原因和分歧处理，不要求固定模型数量。证据不足时扩检、读取原文或澄清，不以未检索到作放行依据。
2. **执行范围控制**：冻结操作对象、参数及内容指纹，执行和发布时重新核对；按规则映射覆盖发送、发布、部署、删除。对已检查且未变化的内容不重复全量检查；明确范围内低风险操作可批量许可，越界后失效。
3. **缓存分层**：分别定义检索、可靠回答、历史判定的缓存键及失效条件，包含相关版本、背景、对象、条件和可见范围；匹配回答仍经轻量交付检查。模型前缀缓存单独配置，未命中或不支持时回到正常模型计算，不改变治理结论。初期内存缓存，多实例时再评估 Redis；验证中文关键词检索和向量检索的实际配合效果。
4. **修订与故障出口**：返回具体问题、依据及再次验收条件；同时限制修订轮次与无进展重试。预算耗尽或故障时写明阻塞原因并供客户端查询，不能静默停住。

项目记忆使用独立写入流程：治理事件留存 → 提取必要背景与决定 → 保存来源、范围及状态 → 供后续检索。状态区分待验证、有效、被纠正、已失效；先检查来源、范围、新鲜度与是否已被取代。纠错时追加记录并追踪受影响记忆、缓存和未完成任务，不直接抹去历史。普通对话不全部塞进上下文，项目记忆也不进入公共知识包。形成 `memory-policy.md`、`cache-policy.md` 和分级复核说明，并测试错误记忆被纠正后不再沿用。

验收：原文缺失、引用失效、条件未满足、内容改动和服务超时均不能伪装通过；输出问题能够返回修订并最终交付或明确阻塞。

## 4. 第四阶段：Agent 中立适配与参考客户端接入

### P8：定义通用适配契约，接入首个参考客户端

先定义模型请求、工具操作、产物和展示四类通用适配契约，再选择首个具备任务、工具及结果拦截能力的参考客户端。参考客户端只用于验证契约，不能成为核心服务依赖或规则前提。

能力表至少列出：原始请求、会话与工作区标识、方案、工具参数、操作前阻止、实际产物、流式缓冲和恢复。无法覆盖的环节公开标记。

模型请求适配负责模型输入输出；Agent 执行适配负责实际工具、产物与交付，两者使用同一项目、任务、运行和步骤关联，避免对同一内容重复治理或重复执行。通用契约不得依赖某个产品的目录、消息格式或 UI。

模型返回 tool call 时，代理把用户授权原话、对话上下文、任务范围和工具参数一起交给治理模型。允许后，记录与该 tool-call ID 绑定的一次性操作许可。执行 Hook 只验证并消费该许可，不重新调用治理模型：宿主保留 `pol2.permit` 元数据时直接消费；宿主裁掉元数据时，用 `session + tool_call_id` 形成的稳定请求号回查同一操作记录并消费。未经过代理、也没有代理记录的直接工具调用才走完整操作治理回退。

实现流式缓冲与发布检查：分段时保留累计上下文，发现跨段风险未闭环则暂不释放相关内容；不能假定已显示内容可以撤回。文件、代码、链接和工具实际结果进入交付清单，按版本检查与释放。验收包括跨段拼接后才显现的问题、检查后文件被修改、单个产物漏送检查及用户取消后的剩余输出。无法覆盖的客户端明确标为部分接入。

验收：真实操作未通过时能阻止；代理外工具调用不能绕过接入控制；参数改变后旧许可失效；子任务沿用正确项目和任务范围；治理服务自身模型调用不递归进入同一治理链；至少两个不同类型的适配器使用同一核心契约并得到一致治理结果。

### P9：跑通真实任务闭环

至少验证以下闭环：

1. 理论问答命中可靠回答并通过轻量交付检查。
2. 持续项目完成需求、方案、执行、测试、结果检查和交付。
3. 输入合理但输出有问题，修订后再交付。
4. 项目切换、工作区多会话、附带问答均正确归属。
5. 操作阻止、超时恢复、重复请求、取消、规则更新和用户质询。
6. 一个含 50 次模型调用和 20 次工具操作的持续任务：全部步骤留痕，普通步骤不重复完整判断，用户默认不超过 3 张卡。

记录新增耗时、各环节模型调用和成本、缓存收益、误拒、漏放、证据召回及修订成功率。一次验证成功不代表全面验收；按照 P3 明确的门槛执行保留测试和故障测试。

## 5. 第五阶段：发布、更新与扩展

### P10：安装和运行验收

分别验证托管与本地部署：

- 首次无知识包显示初始化中；请求可取消或排队，仅在已配置并授权时转交备用服务。
- 有旧稳定包时后台更新；验证成功后原子切换，失败保留旧版。
- 排队任务恢复前检查取消、过期及背景变化。
- 规则更新和纠错失效相关缓存，历史决定保留原依据。
- 生产记录不包含模型凭证；公开解释按数据可见范围输出。

落实知识演进流程：仓库变化检测 → 固定新提交 → 差异及影响分析 → 更新候选解释和案例 → 回归测试 → 发布 → 原子切换。原文修订、解释修订和项目记忆更新分开；本服务不自行改写权威理论。重大变更列出需复核的在途任务，在继续操作前核对新规则；不得在同一决定内无记录混用新旧版本。更新失败保留旧包或执行明确回滚，不能让旧许可在新规则下无条件继续。

对外质询接口返回决定摘要、来源及证据；复核需保留新增证据、维持或修正理由。发布前测试个人资料、第三方内容及凭证不因日志和解释披露而越界。

交付安装说明、配置示例、知识包、验收报告、接入能力表和回滚步骤。逐个扩展 Agent 并单独验收覆盖能力，再依据真实瓶颈优化缓存、检索和并发。
