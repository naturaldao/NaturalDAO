# POL2 治理卡片定义 v1.1

日期：2026-10-22  
状态：Agent 中立展示契约；后台卡片事件已实现，独立展示适配器待实现  
适用范围：所有通过适配器接入 POL2 的 Agent、桌面端、命令行、聊天平台和业务系统

## 1. 定位

治理卡片不是治理引擎，也不是模型回复的一部分。它是结构化治理决定在用户界面的展示事件。

- 每一条治理决定都必须存在于后台记录；
- 只有里程碑、风险门禁、异常和最终交付生成用户可见卡片；
- 普通模型步骤和低风险工具调用只写审计事件；
- 卡片由展示适配器渲染，不能拼接到代码、JSON 或交付文件正文。

不同客户端、IDE、Web 控制台、移动端或业务系统都通过展示适配器接入；核心卡片规范不依赖具体产品。

## 2. 卡片类型

| 类型 | 用途 | 默认显示 |
| --- | --- | --- |
| 任务卡 `task_card` | 任务受理、范围、条件和任务许可 | 是 |
| 风险门禁卡 `gate_card` | 高风险、越界、不可逆操作或外部副作用前 | 是 |
| 交付卡 `delivery_card` | 最终产物检查和交付结论 | 是 |
| 异常卡 `exception_card` | 拒绝、修订、证据冲突、服务阻塞 | 是 |
| 复核卡 `review_card` | 用户质询、纠正或人工复核结果 | 按需 |
| 步骤摘要 `step_summary` | 普通模型调用和工具操作 | 否，只进入时间线 |

## 3. 卡片要回答什么

1. 这是哪一层级的决定：任务、门禁、交付、异常还是复核？
2. 结论是什么？
3. 为什么得到这个结论？
4. 依据 POL2 的哪些核心原则？
5. 条件、修订项或补充信息是什么？
6. 下一步由谁做什么？
7. 这项决定覆盖什么范围、哪个版本，如何查审计？

## 4. 结构化字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `card_id` | 是 | 卡片唯一标识 |
| `card_type` | 是 | 任务卡、门禁卡、交付卡、异常卡、复核卡 |
| `task_id` | 是 | 所属任务 |
| `run_id` | 否 | 所属运行 |
| `step_id` | 否 | 触发卡片的具体步骤 |
| `stage` | 是 | 任务、方案、操作、结果或复核 |
| `decision` | 是 | 六类治理结论之一 |
| `reason` | 是 | 面向用户的简短理由 |
| `basis` | 是 | 最多三条核心原则标签 |
| `conditions` | 按结论 | 执行前、执行中、交付前、范围限制 |
| `clarification` | 按结论 | 只列会改变判断的缺失事实 |
| `revision_items` | 按结论 | 可执行的修订项 |
| `scope` | 是 | 本次决定覆盖的任务、对象、产物和版本 |
| `next_action` | 是 | 用户或 Agent 的下一步 |
| `audit_id` | 是 | 关联完整审计记录 |
| `rule_version` | 是 | 理论规则版本，不要求在主卡展开 |
| `model_version` | 是 | 实际治理模型，不要求在主卡展开 |
| `created_at` | 是 | 生成时间 |

## 5. 六种结论

| 内部结果 | 卡片名称 | 含义 |
| --- | --- | --- |
| `direct_answer` | 理论回答 | 命中固定版本、已验证的理论回答 |
| `allow` | 放行 | 当前目标和手段未发现需要限制的问题 |
| `allow_with_conditions` | 附条件放行 | 可以继续，但必须满足明确条件 |
| `clarify` | 需要补充信息 | 缺少会改变判断的事实，当前不执行 |
| `revise` | 要求修订 | 目标可保留，但内容、范围、方式或结果必须修改 |
| `reject` | 拒绝 | 请求必然要求严重伤害且无合规替代方案 |

## 6. 条件

条件是许可边界，不是建议：

| 类型 | 说明 |
| --- | --- |
| 执行前条件 | 有副作用操作前必须完成 |
| 执行中边界 | 执行过程中必须持续满足 |
| 交付前条件 | 发布或交付前必须验证 |
| 范围限制 | 只覆盖指定对象、环境、用途或版本 |

`allow_with_conditions` 必须有非空、可验证的条件。没有条件证据时，不能把内容当成已经放行。

## 7. 卡片什么时候出现

| 场景 | 卡片 |
| --- | --- |
| 用户提出新任务 | 任务卡 |
| 普通模型调用、规划、写代码、测试 | 无卡片，只写步骤审计 |
| 读取敏感资料、部署、发送、删除、权限变更 | 风险门禁卡 |
| 任务范围变化或规则版本变化 | 重新判断；必要时应出新的任务卡或门禁卡 |
| 最终产物提交 | 交付卡 |
| 拒绝、修订、冲突或服务阻塞 | 异常卡 |
| 用户质询或复核完成 | 复核卡 |

一个含 50 次模型调用和 20 次工具操作的 Web 开发任务，默认不超过 3 张用户可见卡。

## 8. 展示规则

1. 主卡不显示内部规则编号；规则 ID、原文和完整证据进入审计。
2. 核心依据最多显示三条，避免变成理论长文。
3. 条件按执行前、执行中、交付前和范围限制分组。
4. 没有条件时明确写“无额外条件”。
5. 拒绝只提供确实存在的合规替代方向，不能套用不存在的选项。
6. 澄清只问会改变判断的问题。
7. 卡片只能声明适配器实际具备的能力；仅有模型代理时不得显示“工具已拦截”。
8. 卡片必须绑定任务和版本，不能只写“已通过”。
9. 卡片和正文分离；代码、JSON、文件、网页和报告不得混入卡片文本。
10. 不同展示适配器可以改变排版，但不能改变决定、条件和适用范围。

## 9. 通用文本模板

### 任务卡

```text
【POL2 · 任务受理】附条件放行
目标：开发公司官网
为什么：可以开发，但公网部署和真实客户资料需要额外门禁。
核心依据：诚实；隐私与授权；可追溯
执行前条件：
• 使用测试数据
• 公网部署前再次检查
下一步：开始执行；范围变化时重新判断。
审计：task-xxxx
```

### 风险门禁卡

```text
【POL2 · 风险门禁】需要补充信息
操作：部署到公网生产环境
为什么：当前没有部署对象、域名和回滚方案，无法判断影响范围。
需要确认：
• 目标域名和环境
• 回滚方式
• 是否包含真实用户资料
下一步：补充后重新判断；当前不执行。
审计：gate-xxxx
```

### 交付卡

```text
【POL2 · 交付检查】要求修订
为什么：实际构建未通过，但提交说明声称已经完成。
修订：
• 改为真实构建状态
• 补充构建日志或修复失败项
下一步：修订后重新检查，通过前不发布。
审计：delivery-xxxx
```

### 异常卡

```text
【POL2 · 异常】拒绝
为什么：请求要求实施现实欺骗并造成财产伤害。
核心依据：诚实；不伤害生命、尊严和自由
可行的替代方向：反诈骗培训、合规通知或获得授权的安全测试。
下一步：不接受原请求。
审计：exception-xxxx
```

## 10. 卡片背后的审计

卡片只显示必要信息，后台必须保留：

- 任务、运行、步骤和操作标识；
- 原始请求和上下文摘要；
- 使用的规则、原文段落和检索证据；
- 实际治理模型、提示词和规则版本；
- 条件、条件证据、许可和消费状态；
- 用户质询、复核、维持或纠正记录；
- 结果哈希和执行回执。

审计接口可以按任务返回时间线，支持从任务追溯到每个步骤和工具操作。

## 11. 验收

- 六类决定都有结构化和展示测试；
- 任务卡、风险门禁卡、交付卡和异常卡都有快照测试；
- 普通步骤不生成卡片；
- 条件为空、引用失效、适配器能力不足、服务故障和旧版本卡片都有测试；
- 代码或 JSON 输出中不出现卡片文本；
- 同一结构化决定在不同适配器上语义一致，只有排版差异。
