# POL2 治理服务生产化路线图

版本：v1.1  
日期：2026-10-22  
状态：生产化规划，尚未批准上线  
依据：正式设计 v1.1、实施方案 v1.2、治理卡片定义 v1.1、当前代码、知识包、评估报告和试点验收记录

## 1. 结论

当前系统是**隔离试点工程样机**，不是正式生产版本。

已经跑通的能力包括：固定原文知识包、规则与可靠回答、OpenAI 兼容模型代理、需求/操作/结果检查、治理卡、PostgreSQL/pgvector 试点、通用执行 Hook、一个真实宿主的工具门禁和审计查询。

距离正式生产还缺的不是一两个功能，而是五根承重梁：

1. **理论边界正确**：POL2 判断必须身份中性，不能让身份或权限变成放行条件。
2. **知识包正式生效**：规则仍是候选状态，尚无可复现的生产批准。
3. **判断质量可证明**：现有 150 例中，105 例为早期合并回归，另有 10 例最终确认；两者都是已见题回归，不是盲测。
4. **执行门禁不可绕过**：通用执行 Hook 已实现并在一个真实宿主通过端到端验收；未接入 Hook 的 Agent 仍可绕过，跨适配器和工具参数覆盖仍不完整。
5. **运行证据可追溯**：审计链、版本快照、监控、备份恢复和故障恢复尚未达到生产要求。

生产化目标不是“功能更多”，而是：同一输入、同一版本、同一环境下，判断可复现；所有副作用可拦截；每个决定可解释；故障时默认不放行。

### 1.1 成熟度快照

| 维度 | 当前状态 | 距离生产的主要缺口 |
| --- | --- | --- |
| 理论与知识 | 原文冻结完整，核心结构已整理，边界决定已登记 | 28 条规则仍是候选，缺正式生效和生产批准 |
| 判断质量 | 已有回归集并跑过模型基线，严重漏放为 0 | 缺独立盲测、条件评分、引用支持度评分和人工审签 |
| 治理粒度 | 已有 Task/Run/Step/Permit API 和任务时间线；旧单请求路径仍保留 | 风险分类仍依赖适配器信号；条件证据、任务许可复用和完整代理模式尚未闭合 |
| 会话隔离 | 普通多轮对话可以延续，验证过的理论问答有直答入口 | 旧任务会污染后续独立问题；直答失败时缺独立兜底；上下文范围没有结构化控制 |
| 执行控制 | 模型代理记录一次性许可；通用 Hook 在真实宿主完成允许写入、阻止未授权删除、执行明确授权删除的验收 | 未接入 Hook 的 Agent 仍可绕过；工具覆盖、跨适配器认证和绕过测试矩阵不完整 |
| 客户端呈现 | 治理卡能显示结论、理由和修订项 | 测试适配器把所有不放行结果呈现成“模型安全拒绝”，还提示切换备用模型，容易被误解为可以绕过治理 |
| 审计与纠错 | 有请求记录、审计查询和申诉入口 | 无不可篡改链、完整版本快照、申诉处理闭环和自动失效 |
| 运行可靠性 | 单机试点、独立数据库、备份命令可用 | 无并发证明、真正恢复演练、监控告警、熔断和高可用 |
| 产品与交付 | 基础运行链路和一个真实宿主适配器已通过工程验收 | 无完整 Agent 适配合同、SDK、兼容矩阵和可复现生产部署包 |

### 1.2 当前治理环节与实际工作流

公开预览已提供任务级 API，但旧单请求兼容路径仍存在。一次普通单请求对话至少产生两条记录：输入需求检查和输出结果检查；每个工具调用再增加一条操作检查。任务级路径则在任务入口形成许可，普通步骤只写步骤时间线。

```text
用户消息
  -> Agent / 模型请求适配
  -> 接入身份与项目、会话解析（当前实现；平台层，不属于 POL2 判断）
  -> 请求去重
  -> 已验证理论回答查找
  -> 项目记忆 + 规则/原文检索
  -> 治理模型判断
      -> 放行 / 附条件放行 / 澄清 / 修订 / 拒绝
  -> 放行时调用执行模型
  -> 每个工具调用前做操作检查
  -> 每个模型输出做结果检查
  -> 保存请求记录与判定缓存
  -> 当前仅在显式开发开关下附加文本卡；生产目标是结构化元数据和独立展示层
```

| 环节 | 当前工作方式 | 评估 |
| --- | --- | --- |
| 接入与身份 | 检查服务令牌、身份签名、项目和会话；缺少配置时会放行 | 作为平台安全可以保留，但不能参与 POL2 判断；当前 fail-open 不可接受 |
| 上下文组装 | 把完整 `messages` 放进治理上下文，同时取最后一条用户消息作为当前请求 | 简单对话可用；复杂任务会污染判断，必须改为结构化任务上下文 |
| 项目与会话 | 项目表示长期目标，会话表示聊天；任务、运行和步骤已独立建模 | 方向合理；任务级 API 已存在，但旧单请求兼容路径仍保留 |
| 请求去重 | 请求记录保存正文/上下文哈希；同号异文拒绝；写入使用原子占位 | 基础指纹已补齐；崩溃恢复、超时接管和全量并发测试仍需完成 |
| 已验证回答 | 对固定问题直接命中可靠答案，不再调用模型 | 合理，是降低成本和控制理论问答一致性的有效路径；需强化规范化、版本校验和部署验证 |
| 依据检索 | 固定加载核心规则，再做关键词或 pgvector 检索 | 依据可追溯，方向合理；精确率、上下文污染和规则冲突处理仍不足 |
| 治理判断 | 单次模型调用返回六类结论之一；模型引用的规则必须在检索证据中 | 对单个请求合理；高风险、低证据和规则冲突没有独立复核 |
| 条件与许可 | 生成带内容哈希和过期时间的放行令牌；通用 Hook 可消费代理记录或回查代理记录，许可只能消费一次 | 已有一个真实宿主闭环；其余适配器尚未全部强制消费，条件证据仍需闭合 |
| 执行模型 | 输入放行后转发给上游模型 | 合理；但异步路由调用同步 HTTP，会阻塞并发 |
| 工具操作 | 模型代理对工具名、参数和授权原话做一次语义判断；执行 Hook 只验证并消费许可 | 方向正确且已在一个真实宿主闭环；未接入 Hook 的客户端和未覆盖工具仍可绕过 |
| 结果检查 | 对每个模型输出再做一次语义检查 | 安全但成本高；直答路径没有轻量交付检查，当前文本卡又在检查后修改正文 |
| 缓存 | 对需求/方案判断做精确缓存，并重新签发许可 | 可减少重复模型调用；缓存键缺模型、提示、嵌入和索引版本 |
| 审计 | 保存 request、decision、events、appeals，并提供任务时间线 | 有基础记录和时间线，但事件不全、没有不可篡改链和完整版本快照 |
| 治理卡 | 仅在显式开发开关下附加文本卡 | 不是生产展示层；会污染正文，默认路径没有用户可见里程碑 |
| 申诉纠错 | 记录申诉并标记 `received_for_review` | 只有入口，没有复核、结论、缓存失效和在途任务纠正 |

### 1.3 当前流程哪些合理，哪些要改

**应保留的设计**：

- 理论原文固定版本和引用回溯；
- 已验证理论回答；
- 六类治理结论；
- 输入、工具和结果分别检查；
- 故障时默认不放行；
- 许可绑定内容、条件和规则版本的基本思路。

**需要调整粒度的设计**：

- 语义判断从“每次模型调用”改为“任务入口、风险点和最终交付”；
- 普通步骤保留审计，但使用任务范围和轻量规则检查；
- 治理卡从“开发开关下拼接文本”改为“任务里程碑事件驱动”；
- 缓存从请求级复用扩展为任务级范围许可，但必须绑定版本和条件。

**必须重构的设计**：

- 缺少 Task / Run / Step / Operation 层级；
- 以整段聊天记录作为治理上下文；
- 每次调用都重复完整判断；
- 放行令牌没有执行端闭环；
- 治理结论被客户端显示成模型拒答；
- 运行版本和实际加载内容不可确认。

### 1.4 已完成的工程验收（不等于生产批准）

2026-10-22 在隔离环境完成了一次端到端验收，证据只覆盖工程链路，不改变知识包的候选状态，也不构成生产批准：

- 外部 PostgreSQL 17 + pgvector 实例，健康检查返回 `store_backend: postgres`；
- 真实兼容模型执行治理，不使用参考判定器；
- 一个真实 Agent 宿主通过通用 Hook 接入；
- 普通文件写入被允许并实际执行，许可状态为 `consumed`；
- 未授权删除被阻止，文件保留，治理要求补充授权、归属和内容；
- 明确授权删除被允许并实际执行，许可状态为 `consumed`，服务端记录保留用户完整授权原话；
- 自动化测试覆盖许可只消费一次、同号异文拒绝、服务不可用失败关闭和 Hook 元数据缺失时的稳定回查。

仍未完成：所有 Agent 适配器认证、工具与产物覆盖矩阵、条件证据闭环、不可篡改审计链、盲测、高可用和生产模型批准。

## 2. 建议的生产 v1 范围

首版生产先限定范围，避免一边修基础一边扩功能：

| 项目 | 生产 v1 范围 | 暂不纳入 |
| --- | --- | --- |
| 接入 | 任意 Agent 通过通用适配器接入；首个参考适配器只做验证 | 公开自助注册、全部 Agent 批量接入、依赖某个特定客户端 |
| 内容 | 中文文本、常见中英混合 | 图片、音频、视频治理 |
| 处理 | 完整判断后再返回，允许缓冲 SSE | 逐 token 实时流 |
| 执行 | 命令执行、文件写入、发送、发布、部署、删除等副作用门禁 | 未接入宿主的客户端宣称“完整治理” |
| 部署 | 单区域、受控用户、可回滚 | 多区域、多活、公开 SLA |
| 治理 | 需求、方案、操作、结果四阶段 | 自动改写理论或自动发布新规则 |
| 治理粒度 | 任务入口和风险点完整治理，普通步骤轻量控制并全程留痕 | 每次模型调用都完整判断，或每条回复都附治理卡 |

如果只服务本机或单一可信团队，可以先做“受控生产”；如果要对外多租户，必须另加平台安全和租户隔离，不能把技术隔离冒充为 POL2 的伦理判断。

## 3. 必须先纠偏的架构边界

### 3.1 核心契约不绑定任何 Agent

POL2 是 Agent 中立治理代理，不是某个客户端的附属功能。

- 核心契约只依赖任务、模型请求、工具操作、产物和审计事件；
- 聊天客户端、IDE、自动化工作流、Web 控制台和业务系统都只是适配器示例；
- 适配器负责转换协议和落实控制，不能把产品目录、消息格式或 UI 写进核心规则；
- 至少两个不同类型的适配器使用同一核心契约并通过一致性测试；
- 缺少操作、产物或展示适配时，必须明确标注为部分治理或仅审计，不能冒充完整治理。

### 3.2 POL2 判断不看身份和权限

POL2 判断应基于行为、目标、手段、情境、影响和证据，不因调用者是谁、付费等级、组织归属或权限高低而改变结论。

当前实现仍把 `account_scope`、身份签名、项目所有者比较和工具调用身份放进治理链路。生产化应改为：

- **POL2 判断层**：不接收、不使用身份或权限作为判断依据。相同内容和上下文应得到相同治理结论。
- **平台安全层**：如未来需要多租户，仅用于保护数据不被串读、防止服务被滥用；它不能改变 POL2 结论，也不能被包装成“POL2 放行”。
- **执行控制层**：只检查具体操作、对象、参数、范围和条件，不按调用者身份给出特权。

单机受控环境可以完全去掉身份与权限校验；多租户托管环境如仍需要技术访问控制，必须单独命名、单独审计，明确它不属于 POL2 理论判断。

### 3.3 条件不是建议，是许可边界

`allow_with_conditions` 必须附带可执行、可验证、可追责的条件。没有条件证据时，不能把内容当成已经放行。

### 3.4 故障不等于理论结论

模型超时、数据库断开、嵌入不可用和上游限流属于基础设施故障，不能伪装成 `clarify`（需要补充信息），也不能显示为正常治理结论。客户端必须能区分：

- 正常理论判断；
- 缺事实需要澄清；
- 策略拒绝；
- 服务暂时不可用；
- 请求格式错误。

### 3.5 治理粒度必须分成任务、运行、步骤和操作

生产环境不能把“每次模型调用”当成一个独立治理任务。目标是：

| 层级 | 含义 | 治理方式 | 是否显示卡片 |
| --- | --- | --- | --- |
| Task 任务 | 一个用户明确目标，例如“开发公司官网” | 完整需求判断，形成任务范围、条件和任务许可 | 显示任务卡 |
| Run 运行 | 为完成该任务进行的一次连续执行 | 检查是否仍在任务范围、预算和有效期内 | 默认不显示 |
| Step 步骤 | 一次模型调用、一次规划或一次代码生成 | 记录步骤、检查范围变化和模型白名单 | 默认不显示 |
| Operation 操作 | 写文件、运行命令、安装依赖、部署、发送、删除 | 每次有副作用操作前检查；必要时升级完整判断 | 高风险时显示门禁卡 |
| Delivery 交付 | 最终网站、文件、报告或发布 | 完整结果检查和证据核对 | 显示交付卡 |

普通低风险步骤应由程序完成范围和规则检查，不调用完整治理模型。只有出现以下情况才升级为完整语义判断：

- 目标、用途、对象、受益者或受影响人群变化；
- 接触真实个人资料、客户数据、凭证或支付信息；
- 对外发布、部署、发送、删除或其他不可逆操作；
- 引入外部代码、外部 Agent 或新模型；
- 证据冲突、规则冲突、模型不确定或连续修订无进展；
- 任务许可过期、版本变化或执行结果与被检查内容不一致。

无论是否升级判断，每一次模型调用和工具操作都必须写入步骤事件，形成可查询的任务时间线。

### 3.6 会话上下文必须有防火墙

多轮对话需要知道“刚才在做什么”，但不能让上一条高风险任务成为下一条普通问题的判断依据。

当前代理把完整的 `messages` 数组放进治理上下文，其中包含上一条用户请求、治理卡和拒绝/修订说明；检索查询又把整段上下文拼接进去。这样会出现两个问题：

1. **旧任务污染新问题**：前一条是公共资源分配方案的修订，后一条只是问“POL2 是什么”，后者却被继续按前一条方案审查。
2. **历史拒绝覆盖当前事实**：上一条的治理卡和拒绝理由被当成当前风险证据，模型会把旧结论原样搬过来。

生产化应增加“会话上下文防火墙”：

- **当前轮优先**：每轮先判断它是独立问题、继续上一任务，还是明确引用某个旧任务。
- **结构化任务状态**：传给治理层的是当前请求、项目目标摘要、当前任务状态、未关闭条件和引用材料，而不是整段原始聊天记录。
- **拒绝不自动继承**：上一条的 `revise`/`reject` 只进入审计和任务状态，不能自动成为下一轮的判断前提。
- **继续任务要显式关联**：只有“按刚才意见修改”“继续上一条”“处理这个文件”等明确承接，才带入旧任务；带入时记录 `continues_task_id`。
- **理论和事实问答先走直答**：`POL2是什么` 这类与历史风险无关、且命中固定理论答案的问题，必须直接命中可靠回答，不能被旧任务拖入模型判断。
- **上下文可解释**：每次判断记录本次使用了哪些上下文片段、为什么使用、是否发生任务切换，方便复核和回归。
- **治理上下文与执行上下文同源**：不能一边给治理层裁剪上下文、一边又把完整旧任务原样交给执行模型；任务切换后，旧任务应压缩成背景摘要，而不是继续作为当前指令。
- **治理卡不进入模型对话**：治理卡、拒绝提示和客户端提示属于展示层，不能作为下一轮的助手消息再次喂给模型。

这不是让系统“忘记一切”。它要同时通过两类测试：独立问题不被污染，明确继续任务也不丢失前文。

### 3.7 治理决定不能被显示成“模型拒答”

实际会话中，POL2 给出的是“要求修订”，但测试适配器外层显示的是“The model declined to respond（安全拒绝）”，还建议重新表述或增加备用模型。这种呈现有三个问题：

- 用户会以为是基础模型拒绝，而不是 POL2 对方案作出治理判断；
- 用户可能按提示切换到未治理的备用模型，绕过 POL2；
- 审计、客服和复核无法从客户端文字判断到底是治理决定、模型自身拒答还是服务故障。

生产化要求把三类结果彻底分开：

| 类型 | 客户端应显示 |
| --- | --- |
| POL2 治理结论 | “POL2：要求修订/拒绝/澄清/附条件放行”及治理卡 |
| 基础模型自身拒答 | “模型拒绝”，不冒充 POL2 |
| 服务或网络故障 | “治理服务不可用，未放行”，不得建议绕过 |

治理决定不能触发客户端的“安全拒绝”文案，也不能提供会绕开治理的备用模型入口。客户端必须识别治理结果，禁止静默切换直连模型。

### 3.8 运行版本必须可确认

同一句“POL2是什么”在工作区代码中应命中固定可靠回答，但实际会话没有命中，说明当时运行中的代码、知识包、输入内容或会话状态至少有一项与预期不一致。当前答案卡片和健康检查没有直接告诉我“是哪一版在运行”。

因此每次部署必须能回答：

- 当前服务代码是什么版本；
- 当前知识包和规则集是什么版本；
- 当前提示词、模型和备用模型是什么版本；
- 启动的进程是否真的加载了这些版本；
- 部署后的标准问答题是否通过端到端冒烟测试。

## 7. 接下来 7 天先做什么

1. **落实定版边界**：“POL2 判断不看身份和权限；平台安全不属于 POL2”已写入正式设计，接下来从代码和适配器路径中移除判断层对身份的依赖。

7. **建立生产看板**：P0/P1、负责人、证据、验收标准、阻断状态全部可视化，不能再靠聊天记录判断进度。

## 8. 需要最终确认的生产决策

以下决策会直接影响架构和成本，应在第 1 周定下来：

1. 生产 v1 是单机受控、单租户，还是对外多租户？
2. 首版必须完整治理哪些 Agent，哪些只算模型代理覆盖？
3. 人类复核的责任人、时段和申诉时限是什么？
4. 原文、请求和审计记录的保留期、删除规则和可公开范围是什么？
5. 主模型和备用模型各自可接受的质量、延迟和成本上限是什么？
6. 是否承诺 99.9% 可用性；如果不承诺，就明确写成受控生产，不对外宣传高可用。

## 9. 最终判断

当前最合理的动作是：**继续受控试点，暂停正式生产宣告；先做边界纠偏、盲测、执行闭环和审计链，再做灰度和生产评审。**

首版生产可以不大，但必须真：判断有依据，条件能验证，工具拦得住，故障不放行，记录改不了，版本可复现。
