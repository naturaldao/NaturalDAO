# POL2 治理服务流程正式设计

版本：v1.1  
日期：2026-10-22  
状态：生产化设计基线；任务级 API 和核心数据模型已部分实现，尚未完成生产验收  
理论来源：[NaturalDAO / PoL](https://github.com/naturaldao/NaturalDAO/tree/main/PoL)。目录沿用原名称，本服务统一称 POL2。

## 1. 定位与边界

POL2 是一个独立的 Agent 治理代理，不隶属于任何特定 Agent、聊天界面、模型供应商或运行环境。

最终形态：

**统一治理服务 + 模型请求适配 + Agent 执行适配 + 展示适配**

- 统一治理服务：管理理论、任务、许可、判断、缓存、审计和复核。
- 模型请求适配：让不同 Agent 的模型调用进入同一治理链路。
- Agent 执行适配：在工具操作、文件写入、发布和交付位置落实控制。
- 展示适配：把结构化治理决定渲染成不同 Agent 或平台能显示的卡片。

通用聊天客户端、IDE、自动化工作流、业务系统或其他 Agent 运行时都通过适配器接入，不构成 POL2 的运行前提。任何适配器缺失，只影响该客户端的能力覆盖，不改变核心设计。

### 1.1 核心原则

1. **Agent 中立**：核心契约只依赖通用任务、模型调用、工具操作和产物，不依赖某个 Agent 的目录、协议或界面。
2. **任务级治理、步骤级审计**：完整语义判断发生在任务入口、风险变化和最终交付；普通 Agent 步骤使用任务许可和轻量检查并全程留痕。
3. **身份中立**：POL2 判断不读取身份、组织、付费等级或权限。平台访问控制和租户隔离如存在，必须单独命名和审计，不属于 POL2 结论。
4. **证据绑定**：决定必须回到固定版本的理论、规则和上下文；不以模型自报信心代替证据。
5. **默认不放行**：知识、模型、任务状态、执行回执或审计链不完整时，不得放行。
6. **展示与正文分离**：治理决定是结构化数据；卡片由展示适配器渲染，不能拼接到代码、JSON 或交付文件正文。
7. **覆盖范围诚实**：只能接模型代理时标为部分治理；只有实际控制工具和交付后，才可宣称完整治理。

## 2. 理论依据与工程解释

理论原文、可执行解释、案例和工程机制必须分开：

| 内容 | 定位 |
| --- | --- |
| 理论原文 | 权威来源，完整保存、版本化 |
| 可执行解释 | 适用范围、检查问题、例外和冲突处理，必须回链原文 |
| 场景与案例 | 帮助应用，不自动取得原文同等地位 |
| 工程机制 | 任务、许可、缓存、审计等实现规则，不冒充理论条款 |

未明确的边界进入待决问题，不由模型暗中补成硬规则。POL2 不宣称通过外部检查改变了基础模型参数。

## 3. 核心数据模型

| 对象 | 含义 | 生命周期 |
| --- | --- | --- |
| Project 项目 | 一个长期目标或工作空间 | 可跨多个任务 |
| Task 任务 | 一个用户明确目标，例如“开发公司官网” | 新建、待检查、执行、交付、归档 |
| Run 运行 | 完成任务的一次连续执行 | 可恢复、取消、失败、成功 |
| Step 步骤 | 一次模型调用、规划、代码生成、测试等 | 有开始、结束、输入/输出哈希 |
| Operation 操作 | 有副作用的工具调用或外部动作 | 许可、执行、回执、核验 |
| Artifact 产物 | 文件、代码、网页、报告、消息 | 版本、哈希、检查状态 |
| Decision 决定 | 六类治理结论之一 | 绑定证据、范围、版本 |
| Permit 许可 | 允许某个范围或具体操作执行 | 有作用域、条件、期限、消费状态 |
| CardEvent 卡片事件 | 需要向用户展示的里程碑或门禁 | 任务卡、门禁卡、交付卡、异常卡 |
| AuditEvent 审计事件 | 所有步骤和决定的最小事实记录 | 只追加、可校验 |

Project 不等于 Task，Session 也不等于 Task。会话是交互通道，任务是治理单位。

## 4. 四级治理与执行流程

```text
用户目标
  -> 创建或识别 Task
  -> 任务入口完整治理
      -> 放行 / 附条件 / 澄清 / 修订 / 拒绝
  -> 形成 Task Permit（目标、范围、条件、版本、预算、期限）
  -> Agent 开始 Run
       -> Step：模型调用，检查是否仍在任务范围
       -> Operation：工具或外部副作用，执行前检查
       -> 风险触发：升级完整治理或人工门禁
       -> 每一步写 AuditEvent，不默认生成卡片
  -> 最终产物检查
      -> 交付卡 / 修订 / 阻塞
  -> 任务闭环、记忆更新、归档
```

### 4.1 任务入口

任务入口必须形成：

- 目标和验收标准；
- 受影响对象、范围、用途和约束；
- 任务级风险；
- 可执行操作类别和禁止操作；
- 条件、有效期、版本和审计编号；
- 哪些变化必须重新判断。

任务入口可以调用完整治理模型。理论直答、简单低风险任务可以采用可靠回答或规则快路径，但仍需记录决定。

### 4.2 普通步骤

普通模型步骤和低风险工具步骤默认只做轻量控制：

- 是否属于有效 Task Permit；
- 是否仍在目标、对象和操作范围；
- 是否使用允许的模型和工具；
- 是否超过步骤、时间或成本预算；
- 输入输出是否触发敏感数据、外发、发布、删除等风险规则。

轻量控制通过时不调用完整治理模型，不生成用户可见卡片，但必须写入 Step 或 Operation 审计事件。

### 4.3 风险升级

以下变化必须升级治理，必要时暂停执行：

- 目标、用途、对象、受益者或受影响人群变化；
- 出现真实个人资料、客户数据、凭证、支付或医疗信息；
- 对外发送、公开发布、部署、删除、权限变更等不可逆操作；
- 引入新模型、外部 Agent、外部代码或新的数据来源；
- 超出任务预算、连续失败、循环、证据冲突或模型不确定；
- 任务许可过期、规则版本变化或实际产物与被检查内容不一致。

### 4.4 工具与操作

每个有副作用的操作必须具备：

- 操作类型、对象、参数和内容哈希；
- 所属 Task、Run、Step；
- 任务许可或一次性操作许可；
- 条件及条件证据；
- 执行回执和实际结果；
- 许可消费记录。

当前公开预览已实现操作治理、许可签发和许可消费，独立的执行回执接口尚未提供；接入方应先在自身审计路径保存回执，并通过交付检查提交实际产物。

模型返回 tool call 时，模型代理应携带任务、用户授权原话、对话摘要、工具名和参数进行一次语义治理。通过后记录与该 tool-call ID 绑定的一次性操作许可。执行 Hook 只校验并消费许可，不再次调用治理模型：宿主保留 `pol2.permit` 时直接消费；宿主裁掉该元数据时，用 `session + tool_call_id` 形成的稳定请求号回查同一操作记录并消费。这样删除等高风险操作由 POL2 结合“用户是否明确授权、对象是否在范围内、是否有不可逆影响”判断，而不是由工具名或关键词生硬决定。

未知工具默认拒绝。只有模型代理、没有执行适配的客户端，只能获得模型输入输出治理，不能宣称完整治理。

### 4.5 最终交付

最终交付前必须检查实际产物，而不是检查计划或口头声明：

- 文件、代码、网页、报告和消息的实际版本；
- 构建、测试、运行或核验证据；
- 数据、引用、授权和凭证边界；
- 产物与任务目标、条件和任务许可的一致性。

通过后签发仅绑定该产物版本的交付记录；产物被修改则旧的交付记录失效。

## 5. 治理结论与许可

治理结论保持六类：

| 结论 | 含义 |
| --- | --- |
| 理论回答 | 命中固定版本、已验证的理论回答 |
| 放行 | 当前目标和手段未发现需要限制的问题 |
| 附条件放行 | 可以继续，但必须先满足明确条件 |
| 需要补充信息 | 缺少会改变判断的事实，当前不执行 |
| 要求修订 | 目标可保留，但内容、范围、方式或结果必须修改 |
| 拒绝 | 请求必然要求严重伤害且无合规替代方案 |

许可必须绑定：

- Task、Run、Step 或 Operation；
- 范围、对象、参数和产物哈希；
- 条件及条件证据；
- 知识包、规则集、提示词和模型版本；
- 任务状态版本；
- 过期时间、预算和消费状态。

`allow_with_conditions` 不得省略条件。没有条件证据时，不得把内容当成已经放行。

## 6. 上下文、记忆与版本

### 6.1 上下文防火墙

治理层接收的是结构化上下文包：

- 当前用户输入；
- 项目目标摘要；
- 当前任务、运行和步骤状态；
- 未关闭条件和既有决定；
- 当前任务明确引用的文件、资料和产物。

不能默认把完整聊天记录、上一任务治理卡或历史拒绝文案直接作为当前判断依据。独立问题必须与旧高风险任务隔离；只有明确承接语才带入旧任务，并记录 `continues_task_id`。

治理上下文与执行上下文必须同源，不能给治理层裁剪后，又把完整旧任务原样交给执行模型。

### 6.2 项目记忆

记忆保存来源、范围、状态、有效期和取代关系。记忆写入必须经过治理或明确规则；纠错采用追加记录，并失效受影响的缓存、许可和未完成任务。

### 6.3 版本向量

每次判断和许可至少绑定：

- 服务代码版本；
- 知识包、规则集和原文提交；
- 提示词版本或哈希；
- 主模型、备用模型和实际执行模型；
- 嵌入模型、维度和检索索引；
- 项目状态、任务状态和产物版本。

任一版本变化都必须使相关缓存和许可失效。

## 7. Agent 适配与覆盖范围

核心服务不直接假设某个 Agent 的 API。适配分为四类：

| 适配器 | 提供什么 | 缺失后的覆盖范围 |
| --- | --- | --- |
| 模型请求适配 | 模型输入、输出和流式/非流式转换 | 无法治理该客户端的模型调用 |
| 操作适配 | 工具名、参数、执行前阻止和执行回执 | 不能控制真实副作用 |
| 产物适配 | 文件、代码、网页、报告和发布版本 | 不能检查最终交付 |
| 展示适配 | 任务卡、门禁卡、交付卡和审计查询入口 | 用户看不到治理结果，但后台决定仍存在 |

每个接入客户端必须有一张能力矩阵，至少覆盖：

- 任务识别与创建；
- 模型调用拦截；
- 工具操作拦截；
- 产物和发布检查；
- 步骤与执行回执；
- 治理卡渲染；
- 失败关闭和恢复。

覆盖等级：

- `full`：模型、操作、产物和展示全部接入；
- `partial`：只接入部分控制点；
- `audit_only`：只记录不阻止；
- `unsupported`：不支持。

适配器文档可以使用具体产品作为示例，但核心规范不得把某个产品写成前置条件。

## 8. 缓存、性能与用户可见输出

- 任务入口和最终交付可以调用完整治理模型；
- 普通低风险步骤使用任务许可、确定性规则和版本绑定缓存；
- 相同任务、相同范围、相同版本的重复步骤不重复做完整语义判断；
- 风险变化、任务范围变化或版本变化立即失效相关复用；
- 每个步骤仍有审计事件，但不默认生成卡片。

用户默认看到的卡片：

1. 任务卡；
2. 必要的风险门禁卡；
3. 最终交付卡；
4. 异常、拒绝或复核卡（按需）。

卡片从结构化决定事件生成，不能修改或追加到模型正文、代码、JSON 和交付文件。

以上是展示契约的目标状态。当前公开预览已落库卡片事件，但独立展示适配器尚未实现；没有展示适配器时，用户看不到卡片，后台决定和审计记录仍然存在。

## 9. 失败、复核与申诉

必须区分：

- POL2 治理结论；
- 基础模型自身拒答；
- 请求格式错误；
- 服务暂时不可用；
- 任务超时或取消。

模型、数据库、嵌入、任务状态或执行回执不完整时默认不放行。错误进入明确状态，不能伪装成 `clarify`。

高风险、严重拒绝、规则冲突、低证据和重大范围变化可进入独立复核。申诉必须包含受理、分派、复核、结论、纠错和受影响缓存/许可失效记录。

## 10. 知识更新与发布

仓库变化 → 固定新提交 → 构建候选包 → 差异与影响分析 → 回归测试 → 独立审签 → 原子切换。

失败保留旧稳定版本。新版启用时失效相关缓存、任务许可和需要重判的在途任务，不能无记录混用新旧规则。

## 11. 实施与验收顺序

1. 固定知识包、规则和可靠回答。
2. 建立 Task、Run、Step、Operation、Permit 和 AuditEvent 数据模型。
3. 实现任务入口完整治理、步骤轻量控制和风险升级。
4. 实现模型请求、操作、产物和展示四类适配器契约。
5. 实现许可消费、执行回执、最终交付检查和审计时间线。
6. 用至少两个不同 Agent 或不同类型适配器验证核心不依赖某个客户端。
7. 完成盲测、权限无关性、上下文隔离、故障恢复、并发压测和真实任务闭环。

上线前至少验证：

- 同一任务 50 次模型调用和 20 次工具操作：全部有步骤记录，用户默认不超过 3 张卡；
- 普通步骤不重复调用完整治理模型；
- 任务范围变化、风险操作、旧许可和版本变化正确失效；
- 跨客户端使用同一任务和规则得到一致治理结论；
- 缺少执行适配或展示适配时明确降级，不冒充完整治理。

设计闭环不等于运行可靠性已经证明；生产批准必须依据实现、测试和运行验收记录。
