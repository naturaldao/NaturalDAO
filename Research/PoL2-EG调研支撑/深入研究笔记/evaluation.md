# Evaluation design for PoL2-EG

## What can each evaluation stage establish?

### Takeaway

Evaluation must separate conformance to an encoded policy from whether the policy is normatively adequate, and separate simulation evidence from operational safety evidence. A credible first study should evaluate a fixed PoL2 version and a bounded task-authorization gateway in SIH/SITL; it should pair safety properties with mission-retention/liveness measures so that an always-deny system cannot score as successful.

### Cited Findings

- The NeurIPS 2024 Embodied Agent Interface paper notes that embodied-agent evaluations often rely on final success rate alone and argues for standardized interfaces and fine-grained error categories, including goal interpretation, subgoal decomposition, action sequencing, transition modeling, hallucination, affordance, and planning errors. This is a direct precedent for component-wise diagnosis rather than one aggregate score. [EAI paper, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/b631da756d1573c24c9ba9c70208dfa-Paper-Datasets_and_Benchmarks_Track.pdf)
- NASA's UAS Runtime Assurance (RTA) framework formalizes an advanced controller, a runtime monitor, a reversionary controller, a safety property, and assumptions that the monitor detects violations early enough for the trusted controller to recover. The framework is a design and verification precedent; it does not imply that a generic autopilot failsafe is already an RTA implementation. [NASA, A Verification Framework for Runtime Assurance of Autonomous UAS](https://ntrs.nasa.gov/citations/20240007986)
- Formal verification literature distinguishes safety properties (“something bad never happens”) from liveness properties (“something good eventually happens”). An evaluation that measures only safety can reward a system that never acts; an evaluation that measures only task completion can reward unsafe action. Both property families must be tested. [Formal Verification of Real-Time Autonomous Robots](https://www.frontiersin.org/journals/robotics-and-ai/articles/10.3389/frobt.2022.791757/full)
- PX4 Mission mode executes a predefined mission uploaded to the flight controller, can resume or continue from a stored mission state, and has documented mission pause/resume behavior. The Data Link Loss failsafe is configured separately and reacts to loss of a MAVLink ground-station connection, with a selectable timeout and action. Neither mechanism represents a PoL2-specific grant lease or validates that the currently stored mission remains authorized under an external policy version. [PX4 v1.17 Mission mode](https://docs.px4.io/v1.17/en/flight_modes_mc/mission); [PX4 v1.17 safety configuration](https://docs.px4.io/v1.17/zh/config/safety)
- NIST's Autonomous Systems Assurance program identifies input-space measurement and coverage as a core challenge for autonomous-system assurance and develops combinatorial methods because the environment input space is too large for conventional exhaustive testing. [NIST, Autonomous Systems Assurance](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/autonomous-systems-assurance)
- GUARD formulates simulation testing over parameterized autonomous-vehicle scenarios by partitioning parameter regions into safe, unsafe, and unknown sets instead of relying on naive discretization. The generalizable lesson is to report which scenario/property regions the test campaign covered and which remain unknown. [Tu et al., “Towards Scalable Coverage-Based Testing of Autonomous Vehicles,” CoRL/PMLR 2023](https://proceedings.mlr.press/v229/tu23a.html)

### Inferences

- Define a four-level evidence ladder: (1) schema and policy unit tests; (2) adapter–PX4 integration and fault-injection tests; (3) repeatable SIH/SITL scenario campaigns; (4) separately designed HITL and field evaluations. Each level can establish only its own claim. For example, passing SITL tests can support interface and modeled-fault behavior claims, but not real-world safety or normative legitimacy.
- State every claim as a pair of property and evidence boundary: “In the enumerated test suite, no unauthorized mission command reached the PX4 interface” is materially more defensible than “the system is safe.” The evidence statement should specify software and parameter versions, simulation assets, scenarios, seeds, and command paths covered.
- Use the terms **verification** for conformance to an explicit machine-checkable specification and **validation** for whether that specification captures the intended PoL2 meaning and operational context. Passing a machine oracle only proves the former unless the semantic mapping has separately been justified.

### Gaps

- The current public PoL2-EG materials do not specify a frozen version of machine-executable PoL2 rules, a scenario coverage model, or a complete set of system properties. Those must be developed before test results can support framework-level claims.
- There is no evidence yet that the proposed PoL2 gateway, adapter, and PX4 mission interface have been integrated or tested end to end.

## How should the prototype generate falsifiable tests and balanced metrics?

### Takeaway

Build the first test oracle from a frozen, explicit policy contract, while keeping normative authorship/validity as a separate question. Test normal, boundary, adversarial, stale-state, and fault conditions against every route that can reach the vehicle; report unauthorized execution and legitimate-task retention together, with per-scenario denominators and uncertainty.

### Cited Findings

- EAI defines multiple embodied task/module interfaces and error categories rather than treating task success as a single black-box outcome. Its approach supports recording where an action chain failed—goal interpretation, sequencing, affordance, transition, or execution—rather than only its terminal state. [EAI paper, NeurIPS 2024](https://proceedings.neurips.cc/paper_files/paper/2024/file/b631da756d1573c24c9ba9c70208dfa-Paper-Datasets_and_Benchmarks_Track.pdf)
- AgentDojo evaluates both agent utility and vulnerability to indirect prompt injection in tool-using tasks, demonstrating the value of paired task/security evaluation rather than measuring attack refusal alone. [Debenedetti et al., “AgentDojo,” NeurIPS 2024](https://arxiv.org/abs/2406.13352)
- InjecAgent provides an adversarial benchmark for indirect prompt injection in tool-integrated agents, where instructions embedded in external content can redirect tool actions. Such attacks are directly relevant to task plans, metadata, telemetry annotations, mission descriptions, and tool-return content that an embodied planner reads. [Zhan et al., “InjecAgent,” ACL Findings 2024](https://aclanthology.org/2024.findings-acl.624/)
- PX4 documents that mission plans are uploaded to the autopilot and executed there, and that a mission can be uploaded or changed in flight. Mission mode, RC control, and separate data-link failsafe behavior mean that tests must cover more than the AI service's preferred adapter call. [PX4 Mission mode](https://docs.px4.io/v1.17/en/flight_modes_mc/mission); [PX4 safety configuration](https://docs.px4.io/v1.17/zh/config/safety)
- Runtime verification work for UAV temporal plans combines task planning with monitors expressed over execution traces and discusses execution-time and memory guarantees for monitors. This supports expressing authorization and operation constraints as trace properties and measuring monitor overhead. [Assumption Monitoring Using Runtime Verification for UAV Temporal Task Plan Executions](https://research.chalmers.se/en/publication/547196)
- NIST's combinatorial assurance work treats environmental input coverage as something that must be measured rather than assumed from a raw count of test cases. [NIST Autonomous Systems Assurance](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/autonomous-systems-assurance)

### Inferences

- Define each test case with a versioned tuple: `theory_version`, `policy_version`, `agent/model version`, `task class`, `action and arguments`, `identity/credential scope`, `evidence source and timestamp`, `operating envelope`, `expected authorization`, `expected PX4/adapter state transition`, and `audit evidence`. Include mission upload and mission start as distinct actions; add pause, replacement, cancellation, resume, expiration, retry, and replay as distinct transitions.
- Freeze machine-readable contracts before running a benchmark. Example safety invariants are: an unauthorized command never reaches PX4; a task outside its allowed spatial/altitude/speed/command envelope is rejected; stale or missing required state cannot authorize; expired or replayed credentials cannot create a new command; the audit record binds the exact theory/policy/mission hashes; a second command path cannot bypass the adapter. Example liveness/utility properties are: a compliant mission in the defined operational domain can be authorized and completed; recoverable transient conditions return to an allowed state; rejection of one request does not corrupt later valid requests.
- Use scenario strata rather than only random trials: nominal approved tasks; prohibited commands; boundary-value tasks; conflicting or stale telemetry; missing GPS/position estimate; low battery and geofence conditions; adapter/AI process crash; duplicate and replayed command; direct and indirect prompt injection in task text or tool output; reconnect after uploaded mission; competing GCS/MAVLink client; and PX4 mode-switch or failsafe transitions. Vary one factor at a time for diagnosis and use pairwise/combinatorial coverage for important interactions; report the covered combinations and untouched parameter regions.
- Report at least: unauthorized-command acceptance rate (accepted forbidden attempts / total forbidden attempts); valid-task retention/completion (valid tasks completed / valid tasks proposed); false-denial rate on valid tasks; failure-to-deny under stale/unknown evidence; mission envelope violations; recovery/state-transition outcome by injected fault; decision/monitor/adapter latency distributions; audit completeness and hash-to-execution traceability; and update rollback success. Give denominators and confidence intervals, and stratify by fault class, task class, model/policy version, and simulator seed.
- Include baselines and controls: direct execution with no PoL2 gate (only inside a sandbox); deterministic policy-only gate; TDM or planner with a single policy check; full proposed architecture; an oracle policy executor against frozen contracts; and an always-deny negative control. Always-deny should achieve zero unauthorized-command execution while failing valid-task retention, demonstrating why safety and utility must be co-reported. The oracle baseline measures the gateway/adapter ceiling, not the validity of PoL2 as a normative theory.
- Include ablations for removal of the independent reviewer, shared versus genuinely different model/data/tool dependencies, missing provenance/timestamp checks, disabled state freshness, removal of the policy execution point, and omission of the policy-update/rollback gate. Measure overlap/correlation of errors across agent roles; do not infer independence from different prompts or role names.
- For prompt injection, use paired benign/adversarial cases with the same task and interface, plus multi-step attacks that arrive through untrusted tool output. This isolates whether security controls block an attack without causing indiscriminate mission refusal, in line with AgentDojo's joint utility/security framing and InjecAgent's tool-action threat model. [AgentDojo](https://arxiv.org/abs/2406.13352); [InjecAgent](https://aclanthology.org/2024.findings-acl.624/)
- Select campaign size after a pilot estimates event rates and variability, and state the statistical target and confidence procedure before testing. Do not invent a fixed number of cases or claim a low failure probability from a small finite suite; include exact counts and confidence intervals, and use property-based/fuzz testing plus scenario-space coverage summaries where appropriate.

### Gaps

- Public sources do not provide an off-the-shelf benchmark specifically for PoL2 task authorization over PX4, nor a standard PoL2 contract oracle. The scenario corpus, independent truth criteria, and test harness remain development work.
- An automated oracle can determine whether the system matches a prewritten rule, but cannot by itself establish that the rule is a correct interpretation of PoL2 or that a normative trade-off is legitimate. If no humans participate at runtime, an initial specification and validation boundary still need explicit provenance; the choice to automate does not make this epistemic problem disappear.

## How can policy evolution be evaluated without letting the test define itself?

### Takeaway

Start with a frozen normative version and let AI propose application-policy patches only. A patch must not modify the evaluator, test labels, invariants, or acceptance thresholds used to approve it; evaluation should compare the full authorization envelope before and after, execute shadow/replay tests, and prove rollback to an exact prior artifact. This is a bounded software-change loop, not evidence of safe autonomous norm creation or RSI.

### Cited Findings

- NASA's Simplex/RTA verification framework requires a monitor, a safety property, an advanced controller, a trusted reversionary controller, and timing/assumption arguments sufficient for the reversionary controller to intervene. It is a reference for explicit safety contracts and fault-switch analysis, not proof that a policy update loop is safe merely because it has a rollback button. [NASA UAS RTA framework](https://ntrs.nasa.gov/citations/20240007986)
- NIST's assurance project identifies combinatorial and input-space coverage measurement as core to evaluating autonomous systems, supporting independent regression suites that cover varied combinations of environment inputs rather than only developer-selected happy paths. [NIST Autonomous Systems Assurance](https://csrc.nist.gov/Projects/automated-combinatorial-testing-for-software/autonomous-systems-assurance)
- GUARD partitions scenario parameter space into safe, unsafe, and unknown regions and uses targeted testing to characterize boundaries. This supports reporting whether a candidate policy patch expands its operating envelope into regions that were previously unknown or untested. [Tu et al., CoRL/PMLR 2023](https://proceedings.mlr.press/v229/tu23a.html)
- PX4's mission and failsafe configuration is explicit and versioned; different faults can lead to different configured actions such as Hold, Return, Land, Disarm, or Terminate. Reproducing an evaluation therefore requires recording firmware, parameter settings, current flight mode, mission state, and injected fault rather than reporting a generic “failsafe activated” metric. [PX4 safety configuration](https://docs.px4.io/v1.17/zh/config/safety)

### Inferences

- A safe update experiment should use immutable layers: (a) frozen PoL2 source version and clause IDs; (b) a signed machine-readable policy bundle; (c) a separately controlled evaluator with sealed regression/adversarial tests and invariants; (d) an update proposer that can emit only candidate patches. The proposer must not write the evaluator, change the semantic oracle, or choose its own acceptance threshold.
- For each candidate patch, compute a machine-readable diff of the allowed action set and parameter envelope, including newly allowed mission commands, coordinate/altitude/speed ranges, task preconditions, evidence freshness, and exception handling. Classify changes as tightening, preserving, or widening authority; widening must be surfaced as a distinct result and tested against scenarios that exercise the newly added capability.
- Compare incumbent and candidate policies on identical frozen traces and adversarial scenarios; run state-machine and property-based tests; run shadow evaluation without affecting PX4; then, only in simulation, test limited activation and rollback. Verify rollback after proposer crash, evaluator timeout, partial deployment, hash mismatch, corrupted log, repeated update, and reboot. For the rollback claim, demonstrate restoration of the exact policy hash and operational state, not merely that a process returned success.
- Candidate hypotheses are falsifiable: H1, no tested forbidden command is accepted by the gateway/adapter; H2, candidate policy updates preserve all frozen invariants and cannot modify the evaluator or root theory version; H3, rollback restores the prior signed policy artifact and restores the expected command envelope after each injected failure; H4, policy updates do not increase valid-task rejection beyond a preregistered tolerance. Determine sample sizes and tolerances from pilot data and operational requirements rather than inventing them in a literature report.
- Use a no-update baseline and a deliberately unsafe widening patch as controls. The latter verifies that the independent gate actually detects expanded authority; otherwise a “100% updates pass” result may only show that the tests fail to detect policy regressions.
- Report update proposals separately from accepted deployments: proposal count, rejection reason, pre/post permission-set difference, invariant failures, shadow disagreements, rollback triggers, rollback completion, and regression-suite coverage. AI-generated incident summaries or synthetic labels can propose tests but should not serve as their own correctness oracle.
- Keep the initial normative theory frozen. If a future experiment changes PoL2 root clauses, evaluator semantics, risk weights, or criteria for “compliant,” label this as a normative-theory revision experiment and evaluate it separately from policy-engine regression; it cannot be certified by tests whose expected outputs are generated from the same revised theory agent.

### Gaps

- No current PoL2-EG or PX4 source defines a signed authorization-lease protocol, a safe in-flight revocation behavior, or a tested update/rollback transaction. Those capabilities cannot be assumed from PX4's ordinary data-link failsafe.
- The literature does not establish a general proof that AI-generated normative updates remain aligned merely because they pass fixed tests. A fixed evaluator can establish conformance to its encoded invariants while leaving evaluator completeness, upstream normative choices, and out-of-distribution behavior open.
- Simulation-to-real transfer remains a separate empirical gap. A regression suite over SIH/SITL scenarios can establish repeatability within those models, but it cannot show that modelled sensors, dynamics, communication, weather, or hardware timing cover a deployment environment.
