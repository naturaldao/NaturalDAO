# PoL2存储技术选型建议

## 需求
现在需求如下，请继续从综述中推荐最合适的存储技术：

- 它应用于Agent层。
- 首先，它服务于PoL2（Proof of Love2）治理共识。PoL2就是大语言模型落地应用所必需的门禁。实际上也就是大语言模型的治理层，司职大语言模型的输入和输出的管理，为大语言模型构建出终极的安全性和可靠性。那么这个存储库就是这一治理所需的堪比维基百科的大型理论库。它不仅存储了理论知识，还要不断细化出便于快速检索的知识词库，以同时满足低成本调用和快速调用。值得注意的是，知识词库是在应用（application）开发和使用过程中，由专门的Agent生成和维护的。
  关于大语言模型的输入和输出的治理，简单说明如下：
	1. 基于爱2证明判断输入，即外部请求的需求及讨论的爱恨本质，产生合理的决策。譬如：
	   如果有人（与此人的身份无关）企图获取某种剧毒物质的合成方法，在建立出相应的治理协议前，会予以拒绝。
	   如果有人企图构建量化投资软件，因投资的本质乃仇恨行为，也会予以拒绝。
	2. 大语言模型的输出，也会经爱2证明治理层进行决策。如果出现幻觉、错误、仇恨言论，将会被拦截。同一讨论（需求）必要时经多个大语言模型处理，从中挑选出符合爱2证明的输出，也是可行的协作策略。
- 其二，Agent层是大语言模型的Layer2，它和大语言模型一起形成一个自治型的系统。这个系统将自己开发应用（applications）和各种生产技能，它将用于接管人类所有的工作：从生产到服务全盘接管。它产生的数据也将成为大语言模型训练的文本数据的主要来源，可想而知的是，这里产生的数据量很快就是大语言模型总数据中的主要部分，并且占比也将越来越高。我们现在还不知道大语言模型的训练是否会有一个瓶颈点——它很可能存在，也就是说到达瓶颈点后，增加数据训练带来的提升很小。如果存在这个瓶颈点，那么大语言模型的训练间隔就可以改到很长，而这里产生的后续数据就会兼顾为检索库。
- 综上所述，对这个存储库来说，快速检索的功能还是很重要的。
- 因为是自治系统，加上未来这个系统绝不是部署在地面的，而是构建在地球的太空轨道。那么在自治的条件下，人类就不再具有侵入的可能性！并且其治理机制，即PoL2，本身又是非常严厉的治理机制，任何破坏性行为都逃不过它的法眼——PoL2就是这个项目的安全策略！请不要夹带传统互联网的安全思维来画蛇添足。

冷层：纠删码两阶段更新 TSUE（吞吐 1.5–10.1×，I/O 降到 20%）+ NVMe FDP 放置（WAF ≈1 vs 3，90% 利用率下 1.0 vs 1.81——在轨不能换盘，WAF 就是寿命）+ QLC 保持性 PDA-LSTM（BER −80.4%）。

1. 需求 → 存储指标的翻译
你描述的场景，落到存储系统上会变成六条可测量的约束。这一步很重要，因为"维基百科级"和"快速检索"是两种不同的压力，容易在设计上互相抵消。

读路径在每请求关键路径上。 PoL2 要对输入做需求/意图判定、对输出做幻觉/错误/仇恨拦截，同一讨论还可能多模型并行。这意味着每次 LLM 调用背后是 k 次语义检索 + 1 次判定（k 通常 3–30）。检索延迟不是"后台任务延迟"，而是直接叠加进 TTFT。
写路径持续、增量、不可停机。 词库条目由专用 Agent 在应用开发与使用过程中生成。不能有"重建索引窗口"——在轨自治系统里没有"夜间批处理"这个概念。
证明要求：决策可复算。 "爱2证明"要能被追溯，就意味着某次拒绝/放行必须能重放为：判定 = f(检索到的证据集, 词库版本, 规则版本, 模型版本)。这要求存储提供不可变追加日志 + 可寻址的词库快照。
双用途语料。 未来 Agent 产出的数据将成为 LLM 训练语料的主要部分；若训练存在瓶颈点，后续数据转为检索库。因此同一份字节要同时支持顺序大带宽扫描（训练）与随机低延迟语义查找（检索）。
轨道约束。 散热只能靠辐射，功耗预算紧；无人工维修；辐射环境导致位翻转与介质退化。每 GB 的静态功耗和每瓦的检索吞吐是首要指标，而不是峰值 IOPS。
威胁模型按你的设定。 按你的要求，本建议不引入加密、多租户隔离、零信任、TEE、访问控制矩阵等传统互联网安全设计——人类无物理接入，这类机制只会增加功耗与复杂度而不解决真问题。存储侧真实的三类风险是：(a) 辐射导致的位翻转与介质退化；(b) 决策不可复算；(c) 多 Agent 并发写入导致词库自相矛盾。第 4、5 节分别处理。
2. 首选技术：为什么是「SSD 驻留的可增量更新图向量索引」
2.1 它解决了什么别人解决不了的问题
（1）容量与功耗：把索引的内存占用压到千分之一量级。

纯内存 HNSW 的成本与功耗在轨道场景不可接受；而 d-HNSW（arXiv:2505.11783）证明了一种极端的非对称拆分：用 500 个均匀采样向量在计算侧构建一个 0.373 MB 的 meta-HNSW 做簇分类，把全部 sub-HNSW 与原始浮点向量放在远端内存池，查询时靠 doorbell batching 把非连续簇合并成极少的网络往返——每查询 RDMA 往返次数从 3.547 降到 4.75×10⁻³，延迟相对朴素方案最多降低 117×（SIFT1M）/ 121×（GIST1M）。这个"元索引极小、主体在下层"的结构，正是轨道节点需要的形状：内存里只留路由层，语料主体在 NAND 上。

（2）持续演化：磁盘图索引最大的痛点是"插入会杀死查询"。

NAVIS（arXiv:2605.11523）把这件事量化了：每次插入都必须为新点找到 R=64–96 个邻居（position seeking 占更新时延最高 85%），而取边表时会连带把整块全精度向量读进来——浪费的向量读占每次插入读量的 44.34%、向量写占写量的 74.23%。它的三条对策都值得直接采用：

布局解耦：向量与边表拆成两个文件，边表多条打包进同一 4 KiB 页，向量文件存全精度向量；一次插入从 R+2 次整页写降到 2 次边表页写 + 1 次向量写。
收敛感知的投机重排（CASR）：按 PQ 距离排序候选、分批预取全精度向量，以 top-K 不再变化为早停条件——把全精度向量的读取限制在真正可能入选的候选上。
动态 entrance graph + 面向入口点的边表缓存：复用插入遍历信息，入口图更新耗时不到总时间的 1%；4 GB 缓存下命中率比 LFU 高 19.28 个百分点。
（3）可辩护性：声明式召回率把"误判"变成可配置的契约。

治理层最怕的不是延迟，而是"检索没召回因此判错了，而且无法解释"。VADER（arXiv:2609.38053）的方案是把召回率目标写进查询接口 R_t：执行中在线预测当前召回率，达标即提前终止。实测相对 plain search 最高 24.8×、平均 8.8× 加速，召回相对目标平均偏差 0.04，距 oracle 最优终止点仅差 4.1%。对 PoL2 来说这等价于："每一类判定所需的证据强度"可以作为一个显式参数被审计与调整，而不是埋在调参里。

（4）成本：向量表示可以压得很狠，而不损失治理能力。

PDX（arXiv:2503.04422）把块内布局改成维度主序（默认 block size 64），使距离计算变成"维度优先、多向量并行"的紧凑循环：自动向量化内核平均约 2.0× 手写 SIMD，PDXearch 比 SIMD 版 ADSampling 快 4.6×、比 FAISS IVF_FLAT 快 2.2×、比 Milvus 快 3.5×。它不压缩，但让"不压缩"变得可负担。
量化侧可叠加个体化非均匀量化、CARVQ 组残差量化（arXiv:2510.12721）等；语料中 PDX 明确指出量化 + 垂直布局可以叠加。
词库的"低成本档"用学习型稀疏检索：Vectorium（arXiv:2610.12300）在 90% Accuracy@10 下把倒排索引从 1.87 GiB 压到 0.47 GiB；构建侧可用 Fast-LCMS（arXiv:2608.08615）的 216–740× 加速构造。
（5）双用途：同一份文件既喂训练又喂检索。

NAVIS-Reader 的"向量文件 / 边表文件"分离，恰好对上你的第 4 条需求：向量文件是训练语料（顺序大带宽扫描），边表文件是可重建的派生索引（随机访问）。当训练进入瓶颈期、数据转为检索库时，你不需要做任何数据搬迁——只需要把边表建得更密。

（6）分层演进的大方向已经有共识。 Vector Search for the Future（arXiv:2601.01937）把这条路线总结为：内存驻留 → 静态异构（memory–SSD）→ 弹性多层（memory–SSD–object），并指出每一代架构的瓶颈（算力、内存带宽、SSD 随机 I/O、对象存储延迟/成本）分别催生了对应的一批索引与查询优化技术。你要建的就是第三代：理论库主存储在对象/纠删码层，索引在 SSD，路由层与热集在内存/显存。

元数据单独成层：这一点被明确验证过。Towards Efficient KVC Management（arXiv:2505.21919）用生产 trace 发现 tool&agent 负载里 75% 以上请求的块命中率超过 50%，请求内 86.8% 的块是顺序的（可用 range query），而跨请求的非顺序块中 89% 近似随机——必须同时支持 range query 与随机 get。更关键的是它给出的量级：Redis 的元数据索引延迟 >0.1 ms，而 GPU 显存已预缓存 KVC 时的最小 TTFT 才 0.44–0.56 ms——元数据路径本身就能吃掉 TTFT 预算的 20% 以上。词库的元数据（词条 ID → 版本、证据链、类别标签）必须有自己的、为这种混合访问模式设计的结构。
可迁移的抽象：如果后续要做多节点（例如轨道上多舱段），把远端内存优化从索引代码里剥离到运行时是已被验证的做法——Nox（arXiv:2609.02669）用编译器改写 IR 的方式统一提供远端对象管理、地址翻译与缓存，生成的哈希表比手工优化的 SepHash 快 1.4–16×；且缓存只有索引足迹 30% 时，B+-tree 仍能保持 CXL 下 92%、RDMA 下 83% 的峰值吞吐。"缓存只装 30% 也够用"是轨道功耗预算的关键结论。
3. 配套层（都是支撑，不是替代）
3.1 热层：注意力图 / KV / chunk 复用缓存 —— 直接对应"快速调用"
治理路径的请求天然有热点：同一类输入会反复触发同一批理论条目。把"检索 + prefill"变成"缓存命中"，这是收益最大的一步。

注意力图缓存：AttnCache（arXiv:2510.25979）观察到语义完全不同的句子在不同 layer/head 上仍产生高度相似的 attention map，于是把 map 记忆化进数据库（每层一个 file object、相邻 layer 连续排布、mmap 把分散物理页映射为连续虚拟地址），命中后跳过 Q/K 投影、RoPE 与 softmax，只保留 attn_map × V。GPU 上平均 1.6× 端到端 / 3× attention；阈值 0.99 时命中率 30% 而语义相似度指标只降 2%；10 万条 128 维检索 <0.5 ms，比 self-attention 快 360×。
KV 复用：KVShare（arXiv:2503.16525）在多租户前缀复用上把 TTFT 最多降低 9.39×；KEEP（arXiv:2602.23592）按"记忆更新频率"而非固定长度切分粒度，TTFT 降低 1.74–1.91× 且精度几乎无损——"变化频繁的知识按段独立缓存、相对静态的知识成组缓存"这条规则直接对应你"理论库 + 不断细化的词库"的两层结构。
chunk 级计算复用：Cache-Craft（arXiv:2502.15734）给出的账目最值得记住：生产系统中 prefill 占总推理时间最高 77%，每查询约 30k prefill token 对约 600 decode token，prefill 计算量是 decode 的 19.3×；同一知识库 chunk 会被反复检索（75% 的检索 chunk 被重复处理）。它通过 chunk-cache + 选择性重算把冗余计算降低 51%（相对 SOTA 前缀缓存）/ 75%（相对全量重算），P99 TTFT 降低 3×。
生命周期对齐：TokenCake（arXiv:2510.18586）把缓存生命周期与 Agent 的调用事件对齐（工具调用期间卸载、预测返回时刻预回传），并解决了"非关键路径 Agent 驱逐关键路径 Agent 缓存"的关键性倒置问题（实测 Code-Writer 负载中约 26% 的抢占属此类）。在 PoL2 场景里这就是：治理判定的缓存优先级应高于普通应用请求。
3.2 冷层与语料层：纠删码 + 对象存储 + 放置提示
纠删码更新：TSUE（arXiv:2504.17598）用"前端只把更新 append 到 2 副本 DataLog、后端异步回收合并"的两阶段法，把更新吞吐做到 baseline 的 1.5–10.1×，I/O 操作次数降到 parity-log 方案的 20%。这对"词库持续写入 + 理论库长期保存"的组合很合适。
写放大控制：现代 NVMe 的 FDP（Flexible Data Placement，arXiv:2610.02676）让主机按数据生命周期把写流分配到不同 Reclaim Unit，实测非均匀顺序写下 WAF 保持 ≈1 而传统接口 ≈3，平均延迟 −70%、P99–P99.99 尾延迟 −77%、IOPS 3.3×；高利用率下 FDP 在 90% 预填时 WAF 仍近 1.0 而传统是 1.81。在轨无法更换介质，WAF 直接等于寿命，这一项不是优化而是必需。
QLC 保持性：如果为容量密度选 QLC，PDA-LSTM（arXiv:2511.00075）用 LSTM 学习页数据在相邻 wordline 的最优排布，平均降低 BER 80.4%（相对无排布）/ 21.4%–18.4%（相对 WBVM），且冗余元数据占用为 0（WBVM/DVDS 需要约 1/code-length 的额外空间）。辐射环境下的保持性退化与此同源。
多云/跨域成本：如果未来存在多个轨道节点或地面备份，SkyStore（arXiv:2502.20818）的"写本地、按读复制 + 自适应 TTL"相对六种 baseline 平均便宜 1.4–20×。注意：这里用的是成本模型，不是传统安全假设。
语料治理的结构：OmniTable（arXiv:2609.11148）的"逻辑统一、物理分离"范式值得照搬——把所有来源与派生特征收敛到一张逻辑宽表，物理布局完全可演进；算子融合在约 2.5 PB 批次上把 CPU 小时从 42K 降到 18.5K（−55.9%）、I/O 从 27.3K 降到 7.4K、端到端从 38 h 降到 14 h；治理周期从约 14 天降到约 2.5 天。你的"理论库 → 词库"两级结构，本质就是同一套待治理的派生关系。
3.3 自愈层：无人工维修的自治系统
这一层不能省。人类无法接入等于没有运维，故障恢复必须由系统自己完成。

零 I/O 恢复：AccelPact（arXiv:2609.18178）证明通信故障若发生在已提交的 optimizer 边界，设备内存"静止且未损坏"，恢复的真正障碍只是框架缓存了对旧 process group 的引用——只需换掉 communicator 并就地重绑 33 个引用（恒定 0.493–0.518 ms），即可零 replay 继续。整轮 goodput 相对冷重启 1.197×，fault-to-frontier 2,367 s 对 3,466–3,500 s（1.47×）；而在基线里，每步异步 checkpoint 的延迟开销高达 +656.7%、写流量 3.39 TB/hour。
无 checkpoint 恢复：CheckFree（arXiv:2506.15461）用邻近 stage 权重的梯度范数平方加权平均 + 乱序流水线重建丢失的 pipeline stage，每迭代开销几乎为零（91.32 s 对 checkpointing 91.35 s），5% 故障率下达到收敛需 355.13 h 而 checkpointing 需 558.23 h。这与"轨道上不能频繁写检查点"的约束高度契合。
复制式容错：FTHP-MPI（arXiv:2504.09989）在 8192 进程、MTBF=2000 s 下比 checkpointing 高 18.18%，无故障时库拦截开销 <1.5%。代价是 50% 冗余——在算力不是瓶颈、可靠性才是瓶颈的轨道场景，这笔交换通常划算。
设备内完整性：CSDGuard（arXiv:2504.15293）把故障注入、纠删码编解码与勒索软件检测恢复下沉到计算存储设备内部，576 KiB 输入上 kernel 加速 >3×，端到端延迟最多降 70%。把完整性检查放在离数据最近的层，同时省掉主机 CPU 与一次数据搬运。
4. 关于威胁模型的一个说明（按你的要求）
按你的设定，我不引入加密、租户隔离、零信任、TEE 等传统互联网安全设计。理由不是"不需要安全"，而是威胁面已经换了：

传统互联网假设	你的场景
有恶意人类从网络侧发起攻击	人类无物理接入；输入侧由 PoL2 语义治理
需要防越权读取	不存在"未授权租户"；节点内是同一自治系统
需要加密传输/静态加密	加密只增加功耗与延迟，不解决辐射位翻转
因此存储侧真正需要防的是三件事，分别在第 2 节的纠删码/FDP/PDA-LSTM（介质完整性）、第 2.1(3) 节的声明式召回（判定可辩护）、以及下一节的写入协议（词库自洽）中处理。

唯一需要提醒的是：物理隔离消除了人类侵入，但输入路径仍然是外部语义。这不是"安全"问题，而是 PoL2 自身的判定完备性问题——库中不存在的知识，存储层无法替你补上。这一点在第 6 节列为待验证项。

5. 词库的生成与维护协议（Agent 写入面）
这是你的场景相对标准向量数据库最特殊的部分：词库不是人写的，是 Agent 在生产过程中写出来的。语料里有三条可直接采用的证据。

5.1 写入必须分阶段准入，且有量化阈值
Understanding Stage-Wise Utility-Risk Trade-offs（arXiv:2608.30177）把记忆生命周期拆成写入、管理、检索三阶段做受控实验，结论是硬阈值性质的：

写入覆盖率 θw < 0.3：清洁效用与污染效用同步上升到约 15%–20%，攻击成功率接近 0；
θw = 0.3–0.5：两者升到约 20%–42%，污染成功率一般低于 10%；
θw 超过该区间后急剧分离：清洁效用继续上升，但污染效用从峰值跌到 3%–34%，污染成功率快速升到 37%–64%。
管理阶段：不同策略间清洁效用只变化 3%–5%，而污染成功率变化幅度最大达 62 个百分点——这是全流程中杠杆最大的一个环节。
对你的直接含义：词条准入不能只做"是否相关"，必须做"写入配额 + 分阶段审计"。理论库可以宽进（它是证据来源），词库必须严进（它是判定依据）。

5.2 词条要有链接与演化，而不是孤立条目
A-MEM（arXiv:2502.12110）借 Zettelkasten 卡片盒法，让每条新记忆由 LLM 自动生成结构化笔记（内容、时间戳、关键词、标签、上下文描述、稠密向量、链接集合），写入时先按余弦相似度取 top-k 邻居，再由 LLM 判断是否建链，并触发被链接历史记忆的重写（memory evolution），使整个网络在写入过程中自发演化。效果：相对 MemGPT 在 Temporal 任务上 F1 25.52→45.85、平均 token 长度 16,977→2,520（约 1/6.7）；消融掉 Link Generation 与 Memory Evolution，Multi-Hop F1 从 27.02 掉到 9.65。

"链接 + 演化"正是"从理论库细化出词库"所需的机制：理论条目是外部知识，词条是内部衍生，两者之间的边就是治理推理的路径。

5.3 多模型仲裁要有明确的投票与剪枝规则
你的设定里"同一讨论经多个 LLM 处理、挑选符合爱2证明的输出"，在语料里对应的是多 Agent 共识与内存剪枝：

PBFT-Backed Semantic Voting（arXiv:2506.17338）用语义投票对多 Agent 记忆做剪枝，给出了一种可用的仲裁骨架。
Topology Matters（arXiv:2512.04668）量化了一个容易被忽略的副作用：泄漏率是通信拓扑的函数。Llama-3.1-70B 下 6 节点完全图泄漏率 25.32%，链式 12.95%；链式中相邻节点对 21.80%，而最远节点对仅 1.28%；泄漏在 2–3 轮交互内急升后进入平台。 这不是"安全"问题而是词库自洽性问题：Agent 之间的连接密度会决定信息（以及偏见）在多快的时间内收敛到同质。建议把词库写入 Agent 组织成低直径但受控的拓扑，并记录每条词条的来源链，以便在出现系统性偏移时定位污染源。
5.4 版本化与证明记录（这是 PoL2 的硬需求）
存储层必须让每次判定可重放。建议的记录模式：

代码块

  request_hash        输入指纹（原文 + 讨论上下文）
  evidence[]          命中的理论条目/词条 ID + 各自版本号
  lexicon_snapshot    词库快照指纹（Merkle root）
  policy_version      PoL2 规则版本

配套要求：

词库用可快照的结构（追加日志 + 周期性 Merkle 根），使"当时的词库是什么样"可被证明，而不是"现在的词库是什么样"。
派生索引可重建：边表、量化码等全部是理论原文 + 词条日志的纯函数，任何时候可从 L0 重放重建。这既是容灾手段，也是"证明链"的一部分。
写接口按阶段分离：stage_write（低风险、配额内）→ commit（形成版本）→ evolve（触发链接记忆重写）→ arbitrate（多模型投票）。让不同权限的 Agent 只能调用部分接口，是这套系统内部唯一的"权限"概念——它服务于自洽性而不是防入侵。
6. 为什么不选其他（逐条否决，带证据）
候选技术	否决理由
CXL 内存池化 / 内存机架（arXiv:2607.18141 等）	效果其实很好：HyMCache 在同 DRAM 预算下是本地 LMCache 的 3.0×、PD 分离下 1.45×，DRAM 用量是 Mooncake 的 1/16，容量成本比纯 DDR5 便宜 57.5–59.9 倍。但在轨不可插拔、不可扩容——这套方案的价值恰恰来自"可维护的机械与互连基础设施"。且它相对 1TB 分布式 DRAM 仍有约 30% 性能差距，超过有效 DRAM 缓存后带宽塌缩到约 5 GB/s。可以把"SSD 作为内存语义后端的想法"用在节点内单机分层上，但不要把它当作主存储架构。
HBM / GPU 显存为中心	散热只能靠辐射，静态功耗与热密度都不划算；容量密度远低于 NAND。第 2.1 节已说明正确做法是只剩路由层在内存里。
近存 / 存内计算、模拟 CIM	已有直接反证：GoS（arXiv:2607.29076）测得无保护情况下模拟存内阵列的噪声会让 Qwen3-0.6B 困惑度从 12.35 恶化到 80.98、Llama3.2-1B 从 15.42 恶化到 100.78；虽然只保护 sink+recent 的一小部分（对 8K 序列为 1.56%）就能恢复到 11.95，但这说明介质非理想性会直接转化为模型质量损失。辐射环境会放大这一类风险，而定制芯片在轨无法迭代。列为长线备选，不作首选。
计算存储 / 智能 SSD 做检索加速	在特定形态上是成立的：RecFlash（arXiv:2604.25338）把推荐 embedding 按访问频率重映射到同页并用 plane 级并行，延迟最高降 81%、读能耗最高降 91.9%；SCRec（arXiv:2504.00520）用 BRAM/DRAM/SSD 三级分片 + 张量列车压缩，相对 CPU-DRAM 系统吞吐提升 10.37–55.77×。但这要求负载是"高频小向量查表"。你的理论库检索是低并发、高语义、需要图遍历的形态，收益会大幅收窄（RecFlash 自己也报告低局部性时优势明显收窄）。建议只在词库的"高频词条直查"路径上试用，不作为主干。
学习型索引（PGM / RMI / FITing-Tree）	有直接反证：Poisoning Attacks on the PGM-index（arXiv:2609.02328）表明仅 10% 的对抗键就能让最优分段数膨胀最多 120×（YCSB 上 663 段 → 79.8K 段，索引从 0.021 MB 涨到 1.2 MB），且能迁移到 FITing-Tree（1.25–18.5×）与 PGM++（最多 35770×），而传统 B+-tree 几乎不受影响。在一个无人干预的自治系统里，一个"数据分布一漂移就退化两个数量级且无人发现"的结构是不可接受的。
纯内存向量索引	容量与功耗成本；且失去"向量文件即训练语料"的双用途性质。
纯对象存储直查	延迟不达标（毫秒→秒级差距），且元数据路径会成为 TTFT 瓶颈（第 2.2 节的 0.1 ms 对 0.44–0.56 ms）。
纯稀疏/倒排索引	可作"低成本档"（Vectorium 的 1.87→0.47 GiB），但无法承担语义近似检索；应与向量索引组成混合检索，而不是替代。
7. 地面验证清单（发射前必须跑的指标）
由于在轨无法迭代，建议把以下指标作为准入门槛。评测方法论可直接借用 PRISM（arXiv:2607.21746）的立场——"执行而非模拟"，并以延迟分位数而非峰值吞吐为主指标。

8. 需要承认的不确定性
诚实列出三条我无法从现有证据中回答的问题，它们会直接影响选型：

理论库的"知识密度"未知。 语料中的向量检索工作全部假设"语义近邻 = 相关证据"，但治理判定需要的是规范性强、边界清晰的知识（什么行为在什么条件下构成仇恨/幻觉）。这类知识的检索质量取决于词条的粒度设计，而这在你的场景里没有先例可循。建议在理论库与词库之间单独做一次"判定召回率"的离线评测，而不是沿用通用检索指标。
辐射对 NAND 与索引结构的具体影响没有本文语料的直接证据。 语料里最接近的是模拟存内计算的噪声传播（GoS）与 GPU 显存错误画像，二者都不能直接外推到轨道上的 TLC/QLC NAND。这一项必须靠实机辐照试验，不能靠推断。
"训练瓶颈点是否存在"尚无定论，因此"数据转为检索库"的时机不可预测。架构上应假设两种模式可能随时切换——这正是第 2 节追求"同一份字节同时服务两种访问模式"的原因，也是为什么把边表设计为可重建的派生物、而把向量文件设计为不可变事实。
