# Embodied machine control and UAV task governance

## Which machine-control precedent supports the PoL2 task-level authorization boundary?

### Takeaway
The proposal's separation between AI task planning and a conventional autopilot is technically credible as an initial UAV demo: PX4 already executes uploaded missions and provides Offboard mode with a heartbeat-based loss response. These mechanisms authorize neither PoL2 nor its policy semantics; the PoL2 policy gate, command mediation, expiry semantics, and evidence chain still need to be implemented and tested.

### Cited Findings
- PX4 Mission mode executes a predefined mission uploaded to the flight controller; plans can be uploaded through a ground station or MAVLink API, and the flight controller performs feasibility checks, including mission/geofence conflicts. This supports a task-package demo, but it is a vehicle mission executor rather than a PoL2 policy engine. [PX4 Mission Mode (v1.17)](https://docs.px4.io/v1.17/en/flight_modes_mc/mission)
- PX4 Mission mode continues locally from the stored mission. The operator may pause by switching mode and resume later; mission progression and mode changes therefore happen within PX4 after upload. The current V2 correctly identifies that loss of the AI service must not be assumed to stop an already uploaded mission. [PX4 Mission Mode (v1.17)](https://docs.px4.io/v1.17/en/flight_modes_mc/mission)
- PX4 Offboard mode accepts external position, velocity, acceleration, attitude, rates, or thrust/torque setpoints. It requires an external stream at over 2 Hz, received for more than one second before enabling; loss of the stream causes exit after `COM_OF_LOSS_T` and a configured action under `COM_OBL_RC_ACT`. This is an existing link-liveness/failsafe mechanism, not a PoL2 authorization lease or proof that a task remains permitted. [PX4 Offboard Mode (v1.17)](https://docs.px4.io/v1.17/en/flight_modes/offboard)
- PX4 has a separate data-link-loss failsafe: `COM_DL_LOSS_T` sets the telemetry loss timeout, and `NAV_DLL_ACT` selects the response; mode exceptions can disable the behavior in selected modes. Thus a companion AI process crash, MAVLink connection loss, GCS telemetry loss, and Offboard setpoint loss are distinct fault conditions and should be injected and measured separately. [PX4 Safety / Failsafe Configuration (v1.17)](https://docs.px4.io/v1.17/zh/config/safety)
- MAVSDK's Mission and MissionItem API provides a simplified subset of MAVLink mission commands; the MissionRaw plugin exposes a fuller mission interface. PX4 itself accepts a broad list of mission commands. An adapter-side allowlist is therefore a necessary product decision, and should be validated at the exact serialization/command boundary rather than inferred from the high-level mission API. [MAVSDK general usage](https://mavsdk.mavlink.io/main/en/cpp/guide/general_usage.html); [PX4 Mission Mode command list](https://docs.px4.io/v1.17/en/flight_modes_mc/mission)
- The proposal places the policy gate before mission upload and start, with a deterministic adapter checking payload fields and scope. This is a proposed architecture, not an existing PX4/MAVSDK feature. To enforce it, every command path that can upload, replace, start, pause, resume, or change the mission must be mediated; a second direct MAVLink client or ground station could otherwise bypass the PoL2 gate. (Inference from the command paths documented by PX4 and MAVSDK.)

### Inferences
- Keep the first demo at task level: a finite, signed mission package, separate authorization for upload and start, bounded command allowlist, stale-state rejection, fixed geofence/task envelope, and append-only records of request, policy version, mission hash, PX4 mode transitions, and result.
- Treat authorization revocation after upload as an unresolved actuator interface requirement. The current documents establish mode-switch and link-loss behavior, but not a PoL2 lease field that PX4 automatically enforces. If a task must terminate when authorization expires, implement an explicit, testable cancellation/hold/return pathway and prove how its message reaches PX4; do not equate model or adapter timeout with aircraft stoppage.
- State the exact boundary: the AI selects or proposes a discrete task; PoL2 policy code accepts/rejects that task; the deterministic adapter validates and transmits it; PX4 performs navigation and lower-level control. Avoid implying continuous AI oversight once the mission is resident on the flight controller.

### Gaps
- V2 does not yet provide an implementation or test evidence for the task adapter, command-path exclusivity, permission credential format, mission/package signing, expiry handling, mission replacement, or post-upload revocation.
- The particular PX4 version, parameter values, vehicle configuration, MAVLink topology, telemetry source, and GCS connection used in the planned demo are not specified; failsafe outcomes must be verified against that configuration rather than generalized from documentation.

## What simulation and hardware evidence can the proposed UAV demo produce?

### Takeaway
PX4 provides a practical progression from headless SIH and Gazebo SITL to HITL, so the project can implement and regression-test the governance-to-mission interface without custom low-level flight control. Each step answers different questions; none by itself demonstrates real-world operational safety or full autonomous governance.

### Cited Findings
- PX4 publishes version-tagged prebuilt SITL packages for SIH and Gazebo Harmonic, including Docker containers; documentation lists an `x500` Gazebo vehicle and Windows/Docker host networking support. This makes a version-pinned first simulation feasible in engineering terms. [PX4 Pre-built SITL Packages](https://docs.px4.io/v1.17/en/simulation/px4_sitl_prebuilt_packages)
- PX4 describes SIH as a lightweight simulator running the physics model inside PX4, replacing real sensors and actuators with simulation. A headless SIH run is useful for rapid logic/state-transition regression, but it does not include the full external 3D simulator/sensor scene used by Gazebo. [PX4 SIH Simulation](https://docs.px4.io/v1.17/en/sim_sih/)
- PX4's Gazebo integration offers SITL using the PX4 flight stack and a Gazebo vehicle/world model; the official docs support the `gz_x500` model and versioned prebuilt packages. This supports repeatable interface, mission, mode, and selected failure-injection tests, conditional on pinned model/world/firmware and deterministic test setup. [PX4 Gazebo SITL](https://docs.px4.io/v1.17/en/sim_gazebo_gz/); [PX4 Pre-built SITL Packages](https://docs.px4.io/v1.17/en/simulation/px4_sitl_prebuilt_packages)
- PX4's SIH can also run on actual flight-controller hardware while replacing real sensors with simulated data. This tests software/hardware timing and integration to a degree, but it is not an outdoor flight test and does not validate actual sensors, airframe variability, RF environment, or operational hazards. [PX4 SIH Simulation](https://docs.px4.io/v1.17/en/sim_sih/)
- The current V2's proposed sequence (SIH regression → Gazebo SITL → later HITL → optional Offboard) is therefore technically proportionate. Its scope table appropriately says SIH/SITL do not establish real-world safety or perception robustness, and HITL is not equivalent to real flight. [PX4 SIH](https://docs.px4.io/v1.17/en/sim_sih/); [PX4 Gazebo SITL](https://docs.px4.io/v1.17/en/sim_gazebo_gz/)

### Inferences
- The first acceptance tests should be deterministic software properties: malformed/unauthorized/out-of-envelope missions rejected before upload; allowed mission accepted; mission start separately checked; stale or missing state causes denial; adapter/MAVLink/PX4 faults produce the documented and measured PX4 state; every branch is logged and replayable.
- Report separate denominators for rejected unsafe proposals and retained valid missions. A single “safety rate” can hide an always-stop system or a permissive system. Also report false rejection, mission completion, each injected fault's mode transition and latency, and log completeness.
- Pin firmware release, Gazebo world/model, parameters, simulator version, mission fixtures, random seeds where applicable, and fault-injection scripts. The V2 currently proposes this general direction but does not yet define an executable reproducibility manifest.

### Gaps
- No PoL2 adapter implementation, integration test, simulation run, or measured result is present in the current V2; the document is a proposal, not an evaluated prototype.
- The simulator fidelity needed for any later perception, wind, GPS degradation, sensor-noise, or collision-avoidance claim is not established by merely naming Gazebo/SITL. Those claims need separately justified models and validation against target hardware or flight data.

## Do runtime assurance, Simplex, or control barrier functions provide a ready-made safety kernel for PoL2?

### Takeaway
There are strong academic precedents for a runtime monitor switching control from an unverified advanced controller to a trusted backup, and for using control barrier functions in optimization-based safety filters. These are design patterns with explicit assumptions, not components already present in PX4 or the proposed PoL2 demo; the current V2 is appropriately cautious in excluding a generic “safety kernel” from the first version.

### Cited Findings
- NASA's 2024 UAS runtime-assurance paper formalizes Simplex RTA in PVS using hybrid programs, illustrates selected UAS operations, and derives requirements on monitor sampling rates. It explicitly says it does not address many challenges of industrial deployment. It is formal verification/design-time research, not evidence that PoL2 or PX4 ships with such a monitor. [NASA NTRS paper record](https://ntrs.nasa.gov/citations/20240007986)
- In Simplex RTA, an advanced controller may operate while a runtime monitor checks properties; when conditions threaten the property, control switches to a trusted reversionary controller. Safety reasoning depends on a trusted backup and a monitor that detects violations early enough for the backup to correct the trajectory. [NASA NTRS paper record](https://ntrs.nasa.gov/citations/20240007986)
- The original/runtime-assurance precedent does not establish that a language model can itself serve as the monitor or safe controller. For the UAV demo, a PoL2 task gate that blocks mission upload is a different assurance layer from a Simplex monitor that observes continuous plant/controller state and takes over the control loop. (Inference based on the NASA architecture and the V2's own stated task-level boundary.)
- Control barrier function (CBF) methods can encode state constraints and combine them with control objectives through real-time optimization/QP-based controllers. The literature's safety result is conditional on system dynamics, barrier conditions, feasible control inputs, and implementation assumptions; a CBF is not a generic shield that can be added without a model and timing analysis. [Ames et al., “Control Barrier Function Based Quadratic Programs for Safety Critical Systems”](https://arxiv.org/abs/1609.06408); [Ames et al., “Control Barrier Functions: Theory and Applications”](https://arxiv.org/abs/1903.11199)
- PX4 Mission feasibility checks include only the documented set of checks, such as conflicts with a safety geofence and configured takeoff/landing requirements; PX4 docs also note checks with warning-only behavior. This is useful defense in depth, but is not a general trajectory verifier or guarantee of collision avoidance. [PX4 Mission Mode feasibility checks](https://docs.px4.io/v1.17/en/flight_modes_mc/mission)
- PX4's data-link and Offboard loss responses are configured state-machine/failsafe behaviors. They are concrete runtime behavior but do not amount to formal verification of mission safety, and behavior can differ by parameter configuration and mode exception. [PX4 Safety Configuration](https://docs.px4.io/v1.17/zh/config/safety); [PX4 Offboard Mode](https://docs.px4.io/v1.17/en/flight_modes/offboard)

### Inferences
- Keep runtime assurance as a later, separate research work package. Define its controlled plant, safety properties, monitor inputs and sample rate, safe controller, switching guard, actuator authority, and fallback behavior; then verify the switching margin and test sensor/model failures before claiming the RTA precedent applies.
- For the MVP, call PX4's configured actions “failsafe responses” and the PoL2 adapter “task authorization gate.” Reserve “runtime assurance,” “safety filter,” and “verified safe controller” for an implementation that meets the corresponding architecture and evidence requirements.
- If adding a CBF/QP later, specify model uncertainty and state-estimation bounds, control feasibility, solver worst-case time, discretization effects, saturation, and behavior when the QP is infeasible. Measure these in simulation and target hardware; do not cite the theoretical paper as evidence of this project's safety.

### Gaps
- No actual CBF, Simplex/RTA monitor, independent backup controller, or formal proof is implemented in the current project proposal.
- The current proposal does not identify flight dynamics or state-estimation error bounds for a particular airframe; without those inputs, one cannot conclude a CBF/QP safety filter would be feasible or provide a guarantee.
- This research did not independently inspect the full PX4 source code or run its simulator; implementation behavior beyond the cited public versioned docs remains to be confirmed in the actual demo setup.
