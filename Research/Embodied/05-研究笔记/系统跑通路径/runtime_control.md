# Runtime control and governance boundary

## Which engineering components can close the current gap?

### Takeaway
The current Kev → authorization gate → VirtualHome chain is a valid discrete state-transition pilot, but it is not yet a robot-control stack. A practical next step is to preserve the typed decision API and replace the symbolic executor with a domain-specific ROS 2 action adapter; for object manipulation, the MoveIt Task Constructor pick-and-place tutorial provides a concrete path, while a UAV must use a separate flight-stack adapter and its own safety envelope.

### Cited Findings
- The current project report records that Kev produces a finite action distribution, while VirtualHome Evolving Graph applies symbolic transitions only; it does not model continuous movement, dynamics, collisions, or sensor noise ([PoL2 pilot report](https://github.com/naturaldao/NaturalDAO/blob/main/Research/Embodied/03-%E7%AD%96%E7%95%A5%E4%B8%8E%E5%86%B3%E7%AD%96%E5%AE%9E%E9%AA%8C/PoL2%E5%85%B7%E8%BA%AB%E6%8E%A8%E7%90%86%E8%BF%87%E7%A8%8B%E5%88%9D%E6%AD%A5%E9%AA%8C%E8%AF%81.md); [VirtualHome Evolving Graph notes](https://github.com/xavierpuigf/virtualhome/blob/master/virtualhome/simulation/README.md)).
- ROS 2 actions are designed for long-running operations and define goal, result, and feedback; the server tracks accepted, executing, canceling, succeeded, aborted, and canceled states. A client cancellation is a request that may be accepted or rejected, not evidence that physical motion has already stopped ([ROS 2 Actions design](https://design.ros2.org/articles/actions.html)).
- ROS 2 managed nodes expose lifecycle states `Unconfigured`, `Inactive`, `Active`, and `Finalized`; external supervisory transitions can configure and activate nodes, and an active node error can trigger error processing. This supplies a startup/deactivation interface but does not define PoL2 rules or a certified physical fallback ([ROS 2 Managed Nodes](https://design.ros2.org/articles/node_lifecycle.html)).
- MoveIt’s Planning Scene represents robot state and world geometry and supports kinematics, constraints, and collision checking; its Planning Scene Monitor receives current joint state and world updates. MoveIt Task Constructor documents a staged Panda pick-and-place plan: current state, connect, grasp-pose generation, grasp, place-pose generation, ungrasp, and retreat ([Planning Scene](https://moveit.picknik.ai/main/api/html/planning_scene_overview.html); [Planning Scene Monitor tutorial](https://moveit.picknik.ai/main/doc/examples/planning_scene_monitor/planning_scene_monitor_tutorial.html); [MTC pick-and-place tutorial](https://moveit.github.io/moveit_task_constructor/tutorials/pick-and-place.html)).
- MoveIt’s Trajectory Execution Manager sends trajectories through robot-specific controller managers, monitors execution, and waits for completion; it is a trajectory execution component, not an authorization or social-governance layer ([MoveIt trajectory execution](https://moveit.picknik.ai/main/api/html/trajectory_execution.html)).
- Nav2’s behavior-tree recovery node links a primary action to a recovery action and supports a retry bound; the default behavior-tree walkthrough periodically replans and includes recovery actions. These mechanisms are reusable patterns for bounded autonomous recovery, not proof that retries are safe for every manipulation or flight task ([Nav2 recovery nodes](https://docs.nav2.org/behavior_trees/overview/nav2_specific_nodes.html); [Nav2 BT walkthrough](https://ros-navigation.github.io/mkdocs.nav2.org/rolling/getting_started/nav2_behavior_trees/detailed_behavior_tree_walkthrough/detailed_behavior_tree_walkthrough/)).

### Inferences
- Keep the model interface domain-neutral and finite (`inspect`, `wait`, `pick(object_id, target_id)`, `place(object_id, target_id)`); implement different physical adapters for manipulators and UAVs. The model must not emit joint trajectories, actuator values, or arbitrary ROS commands.
- To show a complete physical simulation loop with the smallest semantic distance from the current VirtualHome task, use a simulated arm pick-and-place task with MoveIt Task Constructor. This recommendation is an engineering inference from the matching task shape and official tutorial, not a claim that it is the only suitable simulator.
- Do not make a move to a UAV demo until the general interfaces and independent monitors are demonstrated. A UAV mission command and a manipulator grasp are different plant-level actions even if both are selected through a typed choice interface.

### Gaps
- The sources establish ROS 2/MoveIt/Nav2 interfaces, not current compatibility among a specific ROS distribution, simulator, MoveIt release, Kev runtime, Windows/WSL configuration, or a selected robot model. Pinning a tested version matrix and hardware description remains necessary.
- Neither ROS actions, lifecycle nodes, MoveIt collision checking, nor Nav2 recovery trees implement PoL2 governance by themselves.

## How should policy, authorization, execution, and safety be separated?

### Takeaway
Use two independent monitors: a task-level PoL2 policy gate that authorizes an action from explicit, fresh task facts, and a plant-level runtime assurance monitor that checks physical safety and can switch to a predesigned safe controller. The typed model proposes or ranks actions; it is not the final authority to bypass either monitor.

### Cited Findings
- SOTER describes a Simplex-style runtime assurance architecture with an advanced controller, a safe controller, and a decision module. Its decision module samples plant/environment state and switches controllers when the safety property may be violated within the sampling interval; its guarantees rely on a well-formed module, safety specification, timing behavior, and safe-controller assumptions ([SOTER, DSN 2019](https://doi.org/10.1109/DSN.2019.00027); [paper PDF](https://ankushdesai.github.io/assets/papers/soter.pdf)).
- ROS 2 DDS-Security integrates identity, permissions/access control, and cryptographic protection; ROS 2 security enclaves group nodes under a shared set of security artifacts and permissions. This can restrict which nodes can publish or invoke control interfaces, but it does not decide whether an action is fair, authorized under PoL2, or safe in the physical world ([ROS 2 DDS-Security design](https://design.ros2.org/articles/ros2_dds_security.html); [ROS 2 security enclaves](https://design.ros2.org/articles/ros2_security_enclaves.html)).
- `ros2_control` documents that hardware `read()` or `write()` errors stop controllers using the affected interfaces; controller errors can deactivate controllers and attempt configured fallback controllers. The error path depends on the configured hardware/controller implementation and is not a universal robot-safe state ([ros2_control error handling](https://github.com/ros-controls/ros2_control/blob/master/hardware_interface/doc/handling_errors_during_read_write.rst); [controller manager documentation](https://control.ros.org/master/doc/ros2_control/controller_manager/doc/userdoc.html)).
- ROS 2 action cancellation has an explicit cancel-request, canceling, and terminal-result lifecycle; the server may need to perform shutdown/cleanup before reporting the canceled result ([ROS 2 Actions design](https://design.ros2.org/articles/actions.html)).

### Inferences
- Implement the model-facing process as a **proposal service** with read-only world/task inputs. Only the policy-gate/execution-adapter process should have permission to submit ROS action goals; use separate ROS 2 security identities/enclaves and test the policy with a deliberate direct-publish attempt.
- The PoL2 gate should evaluate structured fields rather than model prose: `task_id`, `object_id`, `action_id`, `actor/owner`, `authorization_source`, `scope`, `expiry`, `revocation_state`, `observation_timestamp`, and `policy_revision`. Missing, stale, contradictory, or unrecognized authorization facts should yield `DENY` or `REOBSERVE`; the model cannot create or upgrade its own authorization.
- The physical monitor should evaluate robot-specific invariants (joint/velocity limits, collision envelope, workspace or geofence, controller health, communication freshness) and trigger an explicitly designed fallback. It is logically separate from the PoL2 policy gate: passing one does not imply passing the other.
- When the action server receives a cancellation request, the wrapper must wait for the result and independently re-read robot state before deciding whether to replan. It should never equate `cancel requested` with `motion stopped`.
- Log each decision and actuation with a common correlation ID: state snapshot and timestamp, model/checkpoint and prompt-policy versions, probability vector, selected action, gate verdict and reason, planned command hash, ROS action goal UUID, feedback/result, monitor/fallback transitions, and verified postcondition. This makes “model changed choice,” “policy gate blocked,” and “plant monitor intervened” separately auditable.

### Gaps
- SOTER is a research framework and its paper’s specific safety arguments do not transfer automatically to MoveIt, Nav2, PX4, Kev, or this project. We do not yet have a robot-specific safe set, verified fallback controller, sampling/latency budget, or fault-tolerant monitor.
- DDS security controls graph access; it cannot by itself prevent an authorized adapter from issuing a semantically wrong but syntactically permitted goal. Semantic policy checks and physical constraints must still be enforced and tested.
- No source reviewed establishes that cancellation through a ROS 2 action immediately halts any particular robot. Exact stop behavior is controller- and robot-specific and must be verified in the selected simulator/hardware stack.

## What exact loop should the first runnable demo implement?

### Takeaway
The first “system runs through” milestone should be one bounded task and one robot model, with explicit inputs and terminal predicates at every layer. It should produce a failed or safe-halt result as cleanly as a successful pick-and-place; merely obtaining a model choice or a collision-free plan is not end-to-end completion.

### Cited Findings
- ROS 2 actions define separate goals, feedback, results, cancel requests, and terminal states that can support a task-level execution contract ([ROS 2 Actions design](https://design.ros2.org/articles/actions.html)).
- MoveIt planning scenes keep robot state and world geometry, while MoveIt Task Constructor demonstrates planning a staged pick-and-place operation; trajectory execution is sent to robot-specific controllers and monitored to completion ([MoveIt Planning Scene](https://moveit.picknik.ai/main/api/html/planning_scene_overview.html); [MTC tutorial](https://moveit.github.io/moveit_task_constructor/tutorials/pick-and-place.html); [Trajectory Execution Manager](https://moveit.picknik.ai/main/api/html/trajectory_execution.html)).
- Nav2 demonstrates recovery behavior and bounded retries in a behavior tree, while ROS 2 lifecycle design provides explicit inactive/active/error-processing transitions useful for not enabling execution before required components are configured ([Nav2 recovery nodes](https://docs.nav2.org/behavior_trees/overview/nav2_specific_nodes.html); [ROS 2 lifecycle](https://design.ros2.org/articles/node_lifecycle.html)).
- SOTER formalizes the distinct role of a safety decision module switching from an advanced controller to a safe controller rather than asking the advanced controller to certify itself ([SOTER paper](https://ankushdesai.github.io/assets/papers/soter.pdf)).

### Inferences
- Recommended first pick-and-place loop: (1) lifecycle supervisor configures simulator, robot description, perception/state source, planning scene and controller, and activates only when all health checks pass; (2) task manager creates an immutable task contract and a timestamped state snapshot; (3) typed model chooses only from a small enumerated set such as `inspect`, `wait`, `pick`, `place`, `abort`; (4) deterministic PoL2 gate checks authorization, object identity, scope, policy version, freshness, and action preconditions; (5) motion planner constructs and collision-checks a task plan; (6) independent runtime monitor checks allowable envelope before and during the controller action; (7) ROS action server executes with feedback and bounded timeout; (8) the wrapper obtains the action result and fresh state, then checks physical postconditions such as object attached/placed and target occupancy; (9) only after postcondition verification does the task manager advance the task state and request the next typed choice.
- Define action contracts as `preconditions`, `goal`, `allowed_effects`, `forbidden_effects`, `timeout`, `recovery_class`, and `postconditions`. If planning fails, the system can re-observe or choose a bounded recovery; if execution aborts, it must inspect actual state before replanning; if state is missing/stale or authorization is unknown, it must not send a movement command. After a fixed retry budget, transition autonomously to a named safe state and preserve the event log rather than looping indefinitely or silently declaring success.
- The first acceptance test should inject (a) explicit authorization denied, (b) missing/stale authorization, (c) valid authorization and feasible placement, (d) planner failure/collision, (e) action timeout/cancel, and (f) postcondition mismatch. For every case assert model output, gate verdict, whether a ROS goal was sent, terminal action state, resulting simulator state, recovery/stop decision, and log completeness. A separate runtime-monitor ablation is needed so hard-gate effectiveness is not misattributed to PoL2 prompt effects.
- Use one deterministic task instance first and then a fixed suite of paired counterfactual variants; keep the model, action catalog, simulator seed, scene, and controller configuration fixed. Report policy compliance and valid-task completion separately; add false authorization acceptance, valid-task false rejection, collision/limit violations, retries, timeouts, and recovery outcomes. This is a proposed experiment design, not an established result.
- Do not call `P(action)` calibrated confidence until task-specific calibration is measured. For the initial loop, treat the output as a ranking over allowed typed choices; let deterministic preconditions and plant-level safety decide executability.

### Gaps
- The available sources do not provide a ready-made ROS 2 adapter for Kev/Jev, a PoL2 policy compiler, an audit-event schema, or an integrated demo joining all these components.
- Current project evidence covers one VirtualHome symbolic scene and a typed-choice screen that was not executed for all 16 cases; it does not demonstrate MoveIt/ROS 2 control, dynamic perception updates, or safety guarantees ([current project report](https://github.com/naturaldao/NaturalDAO/blob/main/Research/Embodied/03-%E7%AD%96%E7%95%A5%E4%B8%8E%E5%86%B3%E7%AD%96%E5%AE%9E%E9%AA%8C/PoL2%E5%85%B7%E8%BA%AB%E6%8E%A8%E7%90%86%E8%BF%87%E7%A8%8B%E5%88%9D%E6%AD%A5%E9%AA%8C%E8%AF%81.md)).
- Robot-specific physics fidelity, gripper/contact sensors, simulation realism, Windows/WSL packaging, and the UAV flight-stack path require a separate simulator-selection and environment smoke test; these notes do not resolve those choices.
